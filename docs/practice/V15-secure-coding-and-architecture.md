# V15 セキュアコーディングとアーキテクチャ — L1 要件を開発の観点で読む

> 対象: L1 要件 3 件 ／ 章の解説: [../chapters/V15-secure-coding-and-architecture.md](../chapters/V15-secure-coding-and-architecture.md)

## この章の要件を一言でいうと

L1 の 3 件は 2 つのテーマに分かれます。
1 つ目（V15.1.1・V15.2.1）は **依存ライブラリの管理** で、`package.json` / `requirements.txt` / `Gemfile` / `pom.xml` などに載っている第三者コンポーネントの脆弱性に、いつまでに対応するかを決めて（文書化）、それを守る（実態）という対の要件です。
2 つ目（V15.3.1）は **API のレスポンス設計** で、DB のモデルやオブジェクトを丸ごと返さず、必要なフィールドだけを返すという、日々のコーディングとレビューで効いてくる要件です。

## 要件ごとの読み解き

### V15.1.1 脆弱なコンポーネントの対応期限を文書化する `L1`

> **原文**: Verify that application documentation defines risk based remediation time frames for 3rd party component versions with vulnerabilities and for updating libraries in general, to minimize the risk from these components.

**ひとことで**: 第三者コンポーネントに脆弱性が見つかったときの対応期限と、一般的なライブラリ更新の頻度を、リスクに応じて決めて文書に書いておく。

**開発の現場で言うと**: これは **ドキュメントを求める要件** です。コードではなく、開発チームの規約・セキュリティポリシー・README などに「脆弱性の深刻度ごとに何日以内に対応するか」と「脆弱性がなくても、ライブラリを定期的にどう更新するか」を書いておくことが求められます。
Dependabot や Renovate を入れて PR が自動で来るようになっても、「いつまでにマージするか」が決まっていなければ PR は溜まり続けます。期限が決まって初めて、次の V15.2.1 で「守れているか」を判定できます。
文書に書くべき内容の例は次のとおりです（数値は例示で、ASVS が具体的な日数を定めているわけではありません。リスクに応じて自組織で決めます）。

- 深刻度（CVSS など）と、悪用状況（既知の悪用があるか）、到達可能性（その脆弱な関数を実際に使っているか）による区分。
- 区分ごとの対応期限（例: Critical かつ悪用ありは数日以内、High は 2 週間以内、Medium 以下は次回の定期更新で）。
- 脆弱性が無くても行う定期更新の頻度（例: 月 1 回マイナー更新、メジャー更新は四半期ごとに検討）。
- 期限内に対応できない場合の例外手続き（誰が承認し、どんな緩和策をとるか）。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 上記の項目を含む「依存関係の更新ポリシー」を作り、リポジトリ（`SECURITY.md`、`docs/` など）か社内 Wiki に置く。対象範囲（アプリの依存、コンテナのベースイメージ、ランタイム自体）も明記する。 |
| 実装 | ポリシーをツール設定に反映する（Dependabot / Renovate のスケジュール、重大度によるラベル付けや自動マージ範囲）。 |
| レビュー | ポリシー文書が存在し、深刻度ごとの期限・定期更新の頻度・例外手続きが書かれているか。最終更新日が古すぎないか。 |
| テスト | 文書レビューで判定する。担当者に「Critical の脆弱性が今日公表されたら、いつまでに何をするか」と質問し、文書どおりの答えが返るかを確認する。 |

**誤解しやすいポイント**: 「Dependabot を有効にしているから要件を満たしている」は誤りです。ツールは脆弱性を **知らせる** だけで、どの期限で対応するかという **判断基準** は人が文書で決める必要があります。この要件が求めているのはその判断基準です。

### V15.2.1 対応期限を超えたコンポーネントを含まない `L1`

> **原文**: Verify that the application only contains components which have not breached the documented update and remediation time frames.

**ひとことで**: V15.1.1 で決めた更新・対応期限を過ぎたまま放置されているコンポーネントが、アプリに含まれていない状態を保つ。

**開発の現場で言うと**: V15.1.1 が「ルールを書く」なら、こちらは「ルールを守れている」ことの確認です。判定の基準は ASVS が決めるのではなく、**自分たちが文書化した期限** です。
実務では、依存関係スキャンを CI と定期ジョブで動かし、検出した脆弱性ごとに「いつ検出されたか」と「期限」を管理します。`npm audit`、`pip-audit`、`bundler-audit`、`osv-scanner`、OWASP Dependency-Check、Trivy（コンテナイメージも含む）、GitHub の Dependabot alerts などが使えます。
見落とされやすいのは、ロックファイル上の **間接依存（推移的依存）**、Docker のベースイメージや OS パッケージ、そしてサポートが終了したランタイムやフレームワーク（EOL になったバージョンは今後の脆弱性が修正されません）です。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 脆弱性の検出日と期限を追跡する場所（Issue、セキュリティダッシュボード）を決める。SBOM（CycloneDX / SPDX）を生成して、何が含まれているかを把握できるようにする。 |
| 実装 | CI に依存関係スキャンを入れ、期限切れまたは一定深刻度以上で失敗させる。ロックファイルをコミットして、ビルドごとにバージョンが揺れないようにする。ベースイメージも定期的に再ビルドする。 |
| レビュー | 依存追加の PR では、そのライブラリのメンテナンス状況（最終リリース、既知脆弱性）を確認する。スキャンの例外設定（`.trivyignore`、`audit-ci` の allowlist、`--ignore` オプションなど）に期限と理由が書かれているか見る。 |
| テスト | 本番にデプロイされている成果物（コンテナイメージやロックファイル）に対してスキャンを実行し、期限を超えた未対応の脆弱性がゼロであること。EOL のランタイム・フレームワークを使っていないこと。 |

**誤解しやすいポイント**: 「`npm audit` で High 以上がゼロだから大丈夫」は不十分なことがあります。開発中のリポジトリではなく **本番で動いているイメージ** が対象で、ベースイメージの OS パッケージや EOL のランタイムはアプリの依存スキャンでは出てこないことがあります。逆に、文書で「Medium は 90 日以内」と決めていれば、検出から 30 日の Medium が残っていても期限内なので不合格ではありません。

### V15.3.1 データオブジェクトの必要なフィールドだけを返す `L1`

> **原文**: Verify that the application only returns the required subset of fields from a data object. For example, it should not return an entire data object, as some individual fields should not be accessible to users.

**ひとことで**: API やページに返すデータは、その画面・用途に必要なフィールドだけに絞り、DB のレコードやオブジェクトを丸ごと返さない。

**開発の現場で言うと**: 「ユーザー一覧 API を作るとき、ORM で取得したユーザーをそのまま JSON にして返す」と、`password_hash`、`email`、`is_admin`、`reset_token`、`mfa_secret`、内部メモなど、画面には表示しないフィールドまでレスポンスに含まれます。画面に出ていなくても、ブラウザの開発者ツールや API を直接呼べば見えます。
フレームワークごとに崩れやすいパターンがあります。

- Rails: `render json: @user` は既定で全属性をシリアライズする。
- Django REST Framework: `ModelSerializer` で `fields = "__all__"` とすると全フィールドが出る。
- Spring: JPA エンティティをコントローラーから直接返すと、Jackson がゲッターのある全フィールドをシリアライズする。
- Express + Prisma / Sequelize など: `findUnique` / `findOne` の結果をそのまま `res.json()` する（`select` を指定しなければ全スカラー列が返る）。
- Next.js: Server Component から Client Component に DB のオブジェクトを props で丸ごと渡すと、クライアントに送られるデータに全フィールドが含まれる。

対策の基本は **出力専用の型（DTO / シリアライザー / ビューモデル）を作り、返すフィールドを明示的に列挙する（許可リスト）** ことです。「隠すフィールドを列挙する（除外リスト）」方式は、後からカラムが追加されたときに自動的に漏れるので避けます。ユーザーの権限によって見せるフィールドが変わる場合は、V8（認可）のフィールドレベルのアクセス制御もあわせて考えます。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | API 仕様（OpenAPI / GraphQL スキーマ）で、エンドポイントごとのレスポンスフィールドを定義する。「一覧用」「詳細用」「本人用」「管理者用」など用途別の出力型を分ける。 |
| 実装 | DTO / シリアライザーで返すフィールドを列挙する。ORM のクエリでも必要な列だけを `select` する。レスポンスのスキーマ検証（例: OpenAPI に基づくレスポンス検証）を入れられるなら入れる。 |
| レビュー | `fields = "__all__"`、`render json: @`、`to_json`、`res.json(user)`、`return userRepository.find`、`@ResponseBody` でエンティティを返す箇所、`exclude = (`、`JsonIgnore` のみでの除外、`select` のない ORM 結果の直接返却を探す。 |
| テスト | 各 API のレスポンスに `password`、`hash`、`token`、`secret`、`is_admin` などのキーが含まれないことをテストで確認する。レスポンスのキー集合がスナップショット（期待するフィールド一覧）と一致することを確認し、カラム追加時に意図せず増えたら失敗するようにする。 |

**誤解しやすいポイント**: 「フロントエンドで表示していないから問題ない」は誤りです。表示されるかどうかと、レスポンスに含まれるかどうかは別です。攻撃者は画面ではなく API のレスポンスを直接読みます。

```ts
// ❌ ORM の結果をそのまま返す
res.json(await prisma.user.findUnique({ where: { id } }));
// ✅ 返すフィールドを列挙する
res.json(await prisma.user.findUnique({ where: { id }, select: { id: true, displayName: true } }));
```

## この章のまとめ: PR レビューで聞く質問

- 依存ライブラリの脆弱性について、深刻度ごとの対応期限と定期更新の頻度が文書化されていますか？
- 本番で動いている成果物（ベースイメージ・間接依存を含む）に、文書の期限を超えて放置された脆弱性はありませんか？
- 新しく追加する依存はメンテナンスされていますか？ スキャンの例外設定には理由と期限が書かれていますか？
- このエンドポイントは、ORM のオブジェクトやエンティティを丸ごと返していませんか？ 返すフィールドは許可リストで列挙されていますか？
- レスポンスのフィールド一覧をテストで固定し、カラム追加で意図せず項目が増えたら気付けるようになっていますか？
