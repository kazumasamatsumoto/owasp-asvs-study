# V6 認証 — L1 要件を開発の観点で読む

> 対象: L1 要件 13 件 ／ 章の解説: [../chapters/V06-authentication.md](../chapters/V06-authentication.md)

## この章の要件を一言でいうと

「ログイン画面・新規登録・パスワード変更・初期パスワード発行・アカウントのシード投入」のコードを書くときの話です。
L1 の中心はパスワードの扱いで、**長さを重視して文字種ルールを課さない / よく使われるパスワードを拒否する / 入力をいじらずに検証する / パスワードマネージャーを邪魔しない** という、NIST SP 800-63B に沿った「現代的な」パスワードポリシーが求められます。
加えて、総当たり・クレデンシャルスタッフィング対策を**文書化して、その通りに実装する**こと、既定アカウントや秘密の質問を残さないことが含まれます。
ハンズオンは [labs/lab03_password_storage](../../labs/lab03_password_storage/) で試せます。

## 要件ごとの読み解き

### V6.1.1 総当たり対策の設計を文書化する `L1`

> **原文**: Verify that application documentation defines how controls such as rate limiting, anti-automation, and adaptive response, are used to defend against attacks such as credential stuffing and password brute force. The documentation must make clear how these controls are configured and prevent malicious account lockout.

**ひとことで**: ログインへの総当たり・リスト型攻撃をどう防ぐか（レート制限・自動化対策・適応的な応答）と、その設定値を文書に書き、悪意あるロックアウトをどう防ぐかも明記する。

**開発の現場で言うと**: これは**ドキュメントを求める要件**です。「ログイン API に何か制限をかけた」ではなく、設計書・README・ADR などに次を書きます。
- どの単位で数えるか（アカウント単位 / IP 単位 / デバイス単位 / 全体）と、しきい値・時間窓（例: 同一アカウントに 15 分で 10 回失敗）
- しきい値を超えたときの応答（遅延、CAPTCHA、一時ブロック、追加認証など）と解除条件
- 攻撃者が**他人のアカウントをわざとロックさせる**嫌がらせへの対策（例: 恒久ロックはしない、ロック中も正しい認証＋追加確認なら通す）
- どの層で実装しているか（WAF / API ゲートウェイ / アプリのミドルウェア）と設定ファイルの場所

Django・Rails・Express などは標準ではログイン試行回数を制限しないことが多く、django-axes、Devise の `:lockable`、Rack::Attack、express-rate-limit などを導入・設定することになります。IdP（Auth0、Cognito など）を使う場合はそちらの設定を記述します。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 上記の項目を決めて文書化する。ログインだけでなくパスワードリセット・OTP 入力など他の認証経路も対象に含めるか明記 |
| 実装 | 文書の値を設定ファイルや定数に落とし、文書から参照できるようにする（V6.3.1 で検証される） |
| レビュー | 文書と実装の設定値（回数・時間窓・応答）が一致しているか。ロックアウトの仕様に「解除方法」が書かれているか |
| テスト | 文書がない・設定値が書かれていない・ロックアウト濫用への言及がない場合は fail と判定する |

**誤解しやすいポイント**: 「失敗 5 回でアカウントを恒久ロック」は総当たりには効きますが、攻撃者がユーザー名を知っていれば**誰でも他人を締め出せる**ため、原文が求める「悪意あるロックアウトの防止」と衝突します。また IP 単位だけの制限は、多数の IP から少しずつ試すクレデンシャルスタッフィングには効きにくいので、複数の単位を組み合わせる設計を書いておきます。

### V6.2.1 パスワードは 8 文字以上（15 文字以上を強く推奨） `L1`

> **原文**: Verify that user set passwords are at least 8 characters in length although a minimum of 15 characters is strongly recommended.

**ひとことで**: ユーザーが設定するパスワードの最小長を 8 文字以上にする（できれば 15 文字以上）。

**開発の現場で言うと**: 新規登録とパスワード変更（リセット含む）のバリデーションです。Django は `startproject` の設定で `MinimumLengthValidator`（既定 8 文字）が有効になっていますが、Devise など他のライブラリは生成される設定の既定値がこれより短い場合があるので、使っている版の設定を確認してください。
注意したいのは「バリデーションが**どの経路で**実行されるか」です。Django の validator はフォームや `createsuperuser` では使われますが、`user.set_password()` を直接呼ぶ独自 API では呼ばない限り効きません。管理画面からの作成、CSV 一括登録、REST API など経路ごとに確認します。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 最小長を決める（8 以上必須、15 以上を推奨）。MFA の有無やユーザー層を考えて決めた値を仕様に書く |
| 実装 | 長さチェックを 1 つの関数／validator に集約し、登録・変更・リセット・管理者作成のすべての経路から呼ぶ |
| レビュー | `min_length`、`MinimumLengthValidator`、`password_length`、`minlength` の値を確認。`set_password(`・`create_user(` を直接呼ぶ箇所で検証が抜けていないか |
| テスト | 7 文字 → 拒否、8 文字（または設定値ちょうど）→ 受理を、画面と API の両方で確認する |

**誤解しやすいポイント**: 「フロントの `<input minlength="8">` で弾いている」はサーバー側の検証になりません。API に直接 POST すれば短いパスワードを設定できてしまいます。また「長さ」の数え方（バイト数か文字数か）も決めておくと、日本語や絵文字を含むパスワードで挙動がぶれません。

### V6.2.2 ユーザーがパスワードを変更できる `L1`

> **原文**: Verify that users can change their password.

**ひとことで**: ログイン中のユーザーが自分でパスワードを変更できる機能を用意する。

**開発の現場で言うと**: 「パスワードを忘れたとき」のリセット機能とは別に、**ログイン済みの状態から自分で変更できる画面・API** があることが求められます。漏洩が疑われたときにユーザー自身がすぐ対処できるようにするためです。
Django（`PasswordChangeView`）、Devise（`registerable` の編集画面）、Spring Security 系のスターターなど、多くのフレームワーク・認証ライブラリに部品がありますが、**ルーティングやメニューに組み込まなければ存在しないのと同じ**です。自前認証の SPA ではよく作り忘れます。
外部 IdP（Google ログインのみ等）でパスワードを持たない場合は、IdP 側の変更手段に誘導する形になります。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 変更画面・API を機能一覧に入れる。変更後に他のセッションをどう扱うか（V7 章）や通知の有無も決める |
| 実装 | 変更処理でも V6.2.1・V6.2.4・V6.2.5 の検証と、保存時のハッシュ化（V11 章）を通す |
| レビュー | パスワード変更のルートが存在し、認証必須になっているか |
| テスト | ログイン → 変更 → ログアウト → 新パスワードでログインできる／旧パスワードではログインできない、を確認 |

**誤解しやすいポイント**: 「パスワードリセット（メールのリンク）があるから変更機能は不要」ではありません。リセットはメールアカウントの安全性に依存する別経路で、ログイン中のユーザーが現在のパスワードを使って変更する手段とは役割が違います。

### V6.2.3 パスワード変更には現在のパスワードと新しいパスワードを求める `L1`

> **原文**: Verify that password change functionality requires the user's current and new password.

**ひとことで**: パスワード変更時は、新しいパスワードだけでなく現在のパスワードも入力させてサーバーで照合する。

**開発の現場で言うと**: セッションを盗まれた、または共用 PC でログインしっぱなしだった場合でも、攻撃者が**パスワードを書き換えてアカウントを乗っ取れない**ようにするためのものです。
Django の `PasswordChangeForm` は現在のパスワード（`old_password`）を要求します。一方、自作の `PATCH /api/users/me` で `password` フィールドを受け付けるような実装では、現在のパスワード確認が抜けがちです。プロフィール更新 API に password が「ついでに」入っているパターンに注意します。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | パスワード変更は専用のエンドポイントにし、入力項目を「現在のパスワード・新しいパスワード」と定める |
| 実装 | サーバー側で現在のパスワードをハッシュ照合し、失敗時は変更しない。照合失敗にもレート制限をかける（現在のパスワードの総当たり窓口になるため） |
| レビュー | `password` を更新できる箇所をすべて洗い出す（`update(`・`save(`・`permit(:password`・シリアライザの `fields`）。現在のパスワード検証なしで更新できる経路がないか |
| テスト | 現在のパスワード欄を空・誤り・省略（JSON からキーごと削除）にしてリクエストし、すべて拒否されること |

**誤解しやすいポイント**: 「画面には現在のパスワード欄がある」でも、サーバーがその値を**検証せず捨てている**実装が実際にあります。また、パスワード**リセット**（忘れた場合）は現在のパスワードを知らない前提なので対象外ですが、その代わりリセットトークンの安全性が問われます（V6.4 系）。

### V6.2.4 よく使われるパスワード上位 3000 件以上を拒否する `L1`

> **原文**: Verify that passwords submitted during account registration or password change are checked against an available set of, at least, the top 3000 passwords which match the application's password policy, e.g. minimum length.

**ひとことで**: 登録・変更時に、よく使われるパスワードのリスト（ポリシーに合うものだけで 3000 件以上）と照合して拒否する。

**開発の現場で言うと**: `password1`・`12345678`・`qwertyuiop` のように長さの条件は満たしていても、真っ先に試されるパスワードを禁止します。ポイントは「**アプリのポリシー（最小長など）を満たすもの**の上位 3000 件」であることです。最小長 8 文字なのに 6 文字以下を多く含むリストを使うと、実質的に照合される件数は少なくなります。
Django の `CommonPasswordValidator` は同梱のリストと照合しますが、リストの件数と内容がポリシーに合っているかは確認してください。他のフレームワークでは自前でリストを用意するか、ライブラリを使います。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | どのリストを使うか（出典・件数）を決め、最小長でフィルタした後も 3000 件以上残ることを確認する |
| 実装 | リストを最小長でフィルタしてから読み込む。照合は大文字小文字を揃えて行うなど比較方法を決める（保存・検証時のパスワード自体は変えない。V6.2.8） |
| レビュー | 照合が登録・変更・リセットの全経路で呼ばれているか。リストファイルがリポジトリやビルド成果物に含まれているか |
| テスト | `password1`、`12345678`、`iloveyou1` など、ポリシーを満たすがリストにある値で登録・変更 → 拒否されること |

**誤解しやすいポイント**: 「文字種ルール（大文字・数字・記号必須）があるから弱いパスワードは防げる」は誤りです。`Password1!` は文字種ルールを満たしますが、典型的な弱いパスワードです。文字種ルールは V6.2.5 で**禁止**されており、その代わりがこの禁止リストです。なお、漏洩済みパスワードとの照合（Have I Been Pwned など）は L2 の V6.2.12 で別に求められます。

### V6.2.5 文字種の構成ルールを課さない `L1`

> **原文**: Verify that passwords of any composition can be used, without rules limiting the type of characters permitted. There must be no requirement for a minimum number of upper or lower case characters, numbers, or special characters.

**ひとことで**: 「大文字・数字・記号を必ず含める」のような構成ルールを課さず、どんな文字の組み合わせでも使えるようにする。

**開発の現場で言うと**: 昔ながらの「英大文字・小文字・数字・記号をそれぞれ 1 文字以上」の正規表現バリデーションは、この要件に**違反**します。また「記号は `!@#$` のみ」「全角文字不可」「スペース不可」のように**使える文字を制限する**ルールも同様に不可です。
既存システムの移行時に旧ポリシーの正規表現が残っていたり、フロント（Yup / Zod のスキーマなど）にだけ残っていたりすることがあります。
Django の `NumericPasswordValidator`（数字だけのパスワードを拒否）のような既定 validator が、この要件の「どんな構成でも」と衝突しないかもチームで判断しておくとよいでしょう。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | ポリシーを「最小長 + 禁止リスト（+ L2 以上で漏洩パスワード照合）」に置き換える。社内規程が文字種ルールを要求していないかも確認 |
| 実装 | 構成ルールの正規表現を削除する。入力欄の `pattern` 属性、バックエンドの validator、DB 側の制約の三か所を見る |
| レビュー | `[A-Z]`・`[0-9]`・`[^a-zA-Z0-9]` を含むパスワード用正規表現、`pattern=`、`.matches(`、`zxcvbn` のスコアで弾く前に構成チェックしていないかを grep |
| テスト | 英小文字だけ 16 文字、スペースを含むパスフレーズ、日本語や絵文字を含むパスワードが（最小長と禁止リストを満たせば）登録できること |

**誤解しやすいポイント**: 「構成ルールは厳しい方が安全」という直感に反しますが、構成ルールは `Password1!` のような予測しやすいパターンを生むだけで強度にあまり寄与しない、というのが NIST SP 800-63B の考え方です。強度確保は長さと禁止リストで行います。

### V6.2.6 パスワード欄は type=password でマスクする `L1`

> **原文**: Verify that password input fields use type=password to mask the entry. Applications may allow the user to temporarily view the entire masked password, or the last typed character of the password.

**ひとことで**: パスワード入力欄は `type="password"` にしてマスク表示する。一時的に全体を表示する「目のアイコン」や最後の 1 文字の表示は許される。

**開発の現場で言うと**: ログイン・登録・変更・リセットのフォームを作るときの話です。UI コンポーネントライブラリ（MUI、Chakra など）の `TextField` を使う場合も `type="password"` を指定しているかを確認します。
「パスワードを表示」トグルは許されていますが、**一時的**であること（ユーザー操作で表示し、再度隠せる）が前提です。モバイルアプリでは `secureTextEntry`（React Native）など各プラットフォームの相当機能を使います。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | パスワード系フォームの部品を 1 つ作り、全画面で共通利用する方針にする |
| 実装 | `<input type="password" autocomplete="current-password">`（変更・登録では `new-password`）。表示トグルは `type` を切り替える実装にし、既定は非表示 |
| レビュー | `name="password"` や `password` を含む入力欄の `type` を確認。`type="text"` のままのものや、独自のマスク処理（`•` に置換）をしていないか |
| テスト | 各フォームを開いて入力が伏せられていること。ブラウザの DevTools で `type` 属性を確認する |

**誤解しやすいポイント**: 「JavaScript で入力値を `●` に置き換えて表示している」独自実装は、ブラウザのパスワードマネージャーが認識できず V6.2.7 を損ないやすく、IME やアクセシビリティの問題も起こします。標準の `type="password"` を使うのが答えです。

### V6.2.7 貼り付け・パスワードマネージャーを妨げない `L1`

> **原文**: Verify that "paste" functionality, browser password helpers, and external password managers are permitted.

**ひとことで**: パスワード欄への貼り付け、ブラウザのパスワード保存・自動入力、外部パスワードマネージャーの利用を禁止しない。

**開発の現場で言うと**: 「セキュリティのため」として `onpaste="return false"` や `autocomplete="off"` を付けたり、確認用のパスワード欄への貼り付けを禁止したりする実装が、この要件に反します。パスワードマネージャーを使えないと、ユーザーは覚えやすい短いパスワードを使い回すようになるからです。
パスワードマネージャーが正しく動くには、`<form>` 内に `type="password"` の欄があり、ユーザー名欄に `autocomplete="username"`、パスワード欄に `current-password` / `new-password` が付いていると判別されやすくなります。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 貼り付け禁止・自動入力禁止を仕様に入れない。社内のセキュリティチェックリストに逆の項目が残っていないか確認する |
| 実装 | 適切な `autocomplete` 属性を付ける。ログインフォームを複数ステップ（ユーザー名 → パスワード）に分ける場合も、マネージャーが認識できる構造にする |
| レビュー | `onpaste`、`paste` イベントの `preventDefault`、`autocomplete="off"`、`oncopy`/`oncut` の抑止、`readonly` を一時的に付けて自動入力を阻む hack を grep |
| テスト | 各パスワード欄にクリップボードから貼り付けられること。ブラウザ標準のパスワード保存と自動入力、主要なパスワードマネージャーの拡張機能で入力できることを手動で確認 |

**誤解しやすいポイント**: 「貼り付け禁止はボットや盗み見対策になる」と思われがちですが、ボットは DOM に直接値を入れるので貼り付け禁止は無関係で、正規ユーザーの安全な行動だけを妨げます。

### V6.2.8 受け取ったパスワードをそのまま検証する `L1`

> **原文**: Verify that the application verifies the user's password exactly as received from the user, without any modifications such as truncation or case transformation.

**ひとことで**: パスワードを切り詰めたり、大文字小文字を変換したりせず、受け取ったとおりの値で検証する。

**開発の現場で言うと**: 意図せず「加工」が入る場所が複数あります。
- **フォームライブラリの前後空白除去**: 例えば Django の `forms.CharField` は既定で `strip=True` です（Django 組み込みの認証フォームのパスワード欄は `strip=False`）。独自フォームでは要確認
- **ハッシュアルゴリズムの長さ制限**: bcrypt は入力の先頭 72 バイトしか使わないため、それより長いパスワードは後ろが無視される（＝切り詰め）。Rails の `has_secure_password` のように 72 バイト超を拒否する実装もある
- **ユーザー名と一緒に `.toLowerCase()`** してしまうコード、DB カラムの長さ制限での切り捨て

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 最大長を決める（L2 の V6.2.9 では 64 文字以上の許可が必要）。bcrypt を使う場合は 72 バイト超をどう扱うか（拒否 or 事前ハッシュ等）を決める |
| 実装 | パスワードには `trim()`・`strip()`・`lower()`・`substring()` をかけない。フォーム／シリアライザのフィールド設定を明示する |
| レビュー | `password.strip(`、`password.trim(`、`.lower(`、`.downcase`、`[:72]`、`substring(0,`、`strip=True` のパスワード欄、`varchar(…)` に平文が入る箇所を grep |
| テスト | 末尾にスペースを付けたパスワードで登録 → スペースなしでログインできない。大文字小文字を変えるとログインできない。73 バイト以上のパスワードで、73 バイト目以降だけ変えた値でログインできない（bcrypt の切り詰め確認） |

**誤解しやすいポイント**: 「末尾スペースを取り除くのはユーザーへの親切」と考えがちですが、要件は加工を認めていません。また「長いパスワードもちゃんと受け付けている」と思っていても、bcrypt で切り詰められていれば 73 バイト目以降は検証されていません。

```python
# ❌ 加工してから検証
check_password(request.POST["password"].strip(), user.password)
# ✅ 受け取ったまま
check_password(request.POST["password"], user.password)
```

### V6.3.1 総当たり対策を文書どおりに実装する `L1`

> **原文**: Verify that controls to prevent attacks such as credential stuffing and password brute force are implemented according to the application's security documentation.

**ひとことで**: V6.1.1 で文書化したレート制限・自動化対策を、その設定どおりに実装し、実際に効いていることを確かめる。

**開発の現場で言うと**: ログイン API を素の状態で公開すると、漏洩したメールアドレスとパスワードの組を大量に試されます（クレデンシャルスタッフィング）。django-axes、Devise `:lockable`、Rack::Attack、express-rate-limit、Spring なら Bucket4j のようなライブラリ、または WAF / API ゲートウェイのレート制限で実装します。
よく漏れるのは「**ログイン以外の認証経路**」です。モバイル用 API、旧バージョンの API、Basic 認証のエンドポイント、パスワードリセット後のログイン、OTP 入力などが抜けていないか確認します。
レート制限のキーにする IP を `X-Forwarded-For` から取る場合、信頼できるプロキシの設定をしないとヘッダの偽装で回避されます。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 認証経路の一覧を作り、それぞれにどの制御を適用するか文書（V6.1.1）と対応付ける |
| 実装 | 失敗回数のカウントはサーバー側（Redis など共有ストア）で行う。複数インスタンス構成でもカウントが共有されること |
| レビュー | 文書のしきい値と設定値の一致。ログイン系ルートにミドルウェアが適用されているか。`X-Forwarded-For` の扱い（信頼するプロキシの設定） |
| テスト | 同一アカウントに誤ったパスワードを文書のしきい値+1 回送り、文書どおりの応答（429、遅延、CAPTCHA 要求など）になること。`X-Forwarded-For` を毎回変えても回避できないこと。別経路（モバイル API 等）でも同様に試す |

**誤解しやすいポイント**: 「ログイン画面に CAPTCHA を付けた」だけでは、CAPTCHA を経由しない API エンドポイントが残っていれば意味がありません。また、カウントをセッションや Cookie に保存する実装は、Cookie を捨てるだけでリセットできてしまいます。

### V6.3.2 既定アカウントを残さない `L1`

> **原文**: Verify that default user accounts (e.g., "root", "admin", or "sa") are not present in the application or are disabled.

**ひとことで**: `root`・`admin`・`sa` のような既定アカウントがアプリに存在しない、または無効化されていること。

**開発の現場で言うと**: 「シードデータ（`db/seeds.rb`、Django の fixture、マイグレーション）で `admin` / `admin123` を作っている」「開発用のテストユーザーが本番にも投入される」「管理画面パッケージや CMS が初期管理者を作る」といった形で混入します。ミドルウェアの管理コンソールや DB の初期ユーザーも同じ考え方で見直します（インフラ側は V13 章とも関わります）。
既定アカウントの名前とパスワードは公開情報として出回っているため、真っ先に試されます。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 初期管理者の作成手順を決める（例: デプロイ時に一度だけ CLI で個人名義のアカウントを作り、パスワードはその場で設定） |
| 実装 | シード・fixture の管理者作成を開発環境限定にする（環境変数でガード）。固定パスワードをコードに書かない |
| レビュー | `seeds`、`fixtures`、マイグレーション内の `create_user`/`create_superuser`、`"admin"`、`"root"`、`"password"`、`"changeme"` を grep。`docker-compose.yml` や Helm values の初期ユーザー設定も確認 |
| テスト | 本番相当環境で `admin`/`admin`、`root`/`root`、`admin`/`password` などでのログインを試し、失敗すること。ユーザー一覧に共有の既定アカウントがないこと |

**誤解しやすいポイント**: 「既定アカウントのパスワードは変更してある」だけでは要件を満たしません。原文は「存在しない、または無効化」を求めています。名前が既知の共有アカウントは総当たりの標的になり、誰が操作したかの追跡もできなくなります。

### V6.4.1 初期パスワード・有効化コードは安全に生成し、短命かつ使い捨てにする `L1`

> **原文**: Verify that system generated initial passwords or activation codes are securely randomly generated, follow the existing password policy, and expire after a short period of time or after they are initially used. These initial secrets must not be permitted to become the long term password.

**ひとことで**: システムが発行する初期パスワードや有効化コードは、安全な乱数で作り、パスワードポリシーを満たし、短時間または初回使用で失効させ、そのまま恒久パスワードにさせない。

**開発の現場で言うと**: 「管理者がユーザーを招待して仮パスワードをメールで送る」「新規登録の確認メールにアクティベーションリンクを付ける」「社員アカウントを一括作成する」といった機能です。
よくある問題は、`生年月日` や `社員番号` を初期パスワードにする、`Math.random()` や連番でコードを作る、期限がなく何か月後でも使える、初回ログイン後もパスワード変更を強制しない、などです。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 有効期限（例: 24 時間）、使い捨てにすること、初回ログイン時にパスワード設定を強制することを決める。可能なら仮パスワードではなく「パスワード設定用の使い捨てリンク」にする |
| 実装 | CSPRNG（Python `secrets`、Node `crypto.randomBytes`、Java `SecureRandom`）で生成。DB にはハッシュで保存し、使用時に無効化。初期パスワードでのログインは「パスワード変更画面」以外に進めないようにする |
| レビュー | `random.`、`Math.random`、`rand(`、`uuid1`、`Date.now()` を使ったコード生成。`expires_at` 相当のカラムとチェックの有無。使用後に削除・無効化しているか |
| テスト | 発行したコード・リンクを 2 回使う → 2 回目は拒否。期限を過ぎたものを使う → 拒否。初期パスワードでログイン後、変更せずに他の画面へ遷移できないこと |

**誤解しやすいポイント**: 「UUID を使っているからランダム」とは限りません。UUID v1 は時刻と MAC アドレスに基づき予測可能な部分があります（v4 も実装によって乱数源が異なります）。また「初回ログイン後に変更を**促す**」だけでは不十分で、変更しないまま使い続けられないようにする必要があります。

### V6.4.2 パスワードのヒントや秘密の質問を使わない `L1`

> **原文**: Verify that password hints or knowledge-based authentication (so-called "secret questions") are not present.

**ひとことで**: 「パスワードのヒント」表示や「秘密の質問」（母親の旧姓、初めて飼ったペットの名前など）を機能として持たない。

**開発の現場で言うと**: 古いシステムのリプレースや、パスワードリセットの「本人確認」として秘密の質問を実装しがちな場面で問題になります。秘密の質問の答えは SNS などから調べられたり推測されたりしやすく、ヒントはパスワードそのものを漏らしかねません。
パスワードを忘れた場合は、登録済みのメールアドレスや電話番号などへの使い捨てリンク・コードによるリセット、MFA の回復コードといった別の手段で対応します（MFA を迂回しないことは L2 の V6.4.3）。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | アカウント回復手段から秘密の質問・ヒントを外す。既存データ（質問と答え）の削除計画も立てる |
| 実装 | 登録フォーム・プロフィール編集・リセットフローから該当項目を削除する |
| レビュー | `secret_question`、`security_question`、`password_hint`、`hint` などのカラム・フィールド・画面文言を grep |
| テスト | 登録・プロフィール・パスワードリセットの各画面で、秘密の質問やヒントの入力・表示がないこと。リセット API に質問の答えを送るパラメータが残っていないこと |

**誤解しやすいポイント**: 「秘密の質問は追加の本人確認で、セキュリティを強化している」と考えがちですが、推測・調査可能な情報なので実質的には弱い第 2 のパスワードを増やすだけです。「答えをハッシュ化して保存しているから安全」も、答えの候補が少ないので解決になりません。
