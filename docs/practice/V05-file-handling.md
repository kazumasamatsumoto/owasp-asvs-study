# V5 ファイル処理 — L1 要件を開発の観点で読む

> 対象: L1 要件 4 件 ／ 章の解説: [../chapters/V05-file-handling.md](../chapters/V05-file-handling.md)

## この章の要件を一言でいうと

「ユーザーからファイルを受け取る」「ファイルをディスクやストレージに置く」「パスを組み立ててファイルを開く」コードを書くときの話です。
プロフィール画像のアップロード、請求書 PDF の添付、CSV の一括取り込み、帳票のダウンロードなど、ファイルが絡む機能はどれも対象になります。
L1 で求められるのは 4 つ: **大きすぎるファイルを受け付けない / 拡張子と中身が一致するか確かめる / アップロードされたものをサーバーで実行させない / ユーザー入力でパスを組み立てない**。
ハンズオンは [labs/lab05_file_upload](../../labs/lab05_file_upload/) で試せます。

## 要件ごとの読み解き

### V5.2.1 処理できるサイズのファイルだけ受け付ける `L1`

> **原文**: Verify that the application will only accept files of a size which it can process without causing a loss of performance or a denial of service attack.

**ひとことで**: アップロードには必ず上限サイズを設け、それを超えるファイルは処理を始める前に拒否する。

**開発の現場で言うと**: 「会員がアバター画像を登録する」「管理画面で CSV を取り込む」といった機能を作るとき、上限を決めずに実装すると、数 GB のファイルを並列で送るだけでメモリ・ディスク・ワーカーが埋まります。
フレームワークやミドルウェアの中には既定で上限を持つものがあります（例: nginx の `client_max_body_size`、Spring Boot の `spring.servlet.multipart.max-file-size`、Next.js の Server Actions のボディサイズ上限）。一方、Express の multer の `limits` のように**明示しないと実質無制限**になる設定や、Django の `DATA_UPLOAD_MAX_MEMORY_SIZE` のように**ファイル本体は対象外**の設定もあります。既定値はバージョンで変わるので、使っている版のドキュメントで必ず確認してください。
また「受け付けられるサイズ」は**その後の処理**で決まります。10MB の画像でもサムネイル生成でメモリを数百 MB 使うことがあり、CSV なら行数で処理時間が決まります。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | アップロード機能ごとに上限（例: アバター 2MB、CSV 10MB / 5 万行）を決め、仕様書に書く。後段処理（画像変換・パース）のコストも見積もる |
| 実装 | リバースプロキシ・アプリ・アップロードライブラリの**全層**で上限を設定する。全体を `read()` する前にストリームで数えて打ち切る。リクエスト全体のタイムアウトも設定 |
| レビュー | `request.files[...].read()`、`multer()` で `limits` なし、`await req.arrayBuffer()`、`file.getBytes()` など全量読み込みを探す。上限の値がどこで定義されているかを確認 |
| テスト | 上限ちょうど・上限+1 バイトのファイルを送り、後者が 413 などで拒否されること。`Content-Length` を偽った（小さく申告した）チャンク転送でも打ち切られること |

**誤解しやすいポイント**: 「フロントの `<input>` で 5MB 以上は選べないようにした」は防御になりません。curl で直接送れます。また「nginx で上限を設定した」だけだと、nginx を経由しない経路（内部 API、別のロードバランサ）や、小さなファイルでも重い処理（巨大な行数の CSV、展開すると巨大になる画像）は防げません。

```javascript
// ✅ Express + multer: 明示的に上限を指定する
const upload = multer({
  storage: multer.memoryStorage(),
  limits: { fileSize: 2 * 1024 * 1024, files: 1 },
});
```

### V5.2.2 拡張子と中身が一致するかを確かめる `L1`

> **原文**: Verify that when the application accepts a file, either on its own or within an archive such as a zip file, it checks if the file extension matches an expected file extension and validates that the contents correspond to the type represented by the extension. This includes, but is not limited to, checking the initial 'magic bytes', performing image re-writing, and using specialized libraries for file content validation. For L1, this can focus just on files which are used to make specific business or security decisions. For L2 and up, this must apply to all files being accepted.

**ひとことで**: 「期待する拡張子か」と「中身が本当にその形式か」の両方を、サーバー側で確認する（zip の中身も対象）。

**開発の現場で言うと**: 本人確認書類の画像、経費精算の領収書 PDF、取り込み用の CSV のように、**その内容をもとに業務判断やセキュリティ判断をするファイル**が L1 の最低ラインです（L2 以上ではすべての受け付けファイルが対象）。
Django の `ImageField` は Pillow で画像として開けるかを確認しますが、`FileExtensionValidator` は**拡張子しか見ません**。Rails の Active Storage や Express の multer も、何を許可するかは開発者が決めるもので、既定で中身を検証してくれるわけではありません。
ブラウザが送る `Content-Type`（multer の `file.mimetype`、Rails の `content_type` の申告値など）は**クライアントが自由に書ける値**です。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 機能ごとに許可する拡張子の allowlist を決める（例: `.jpg .png .pdf`）。zip を受け付けるなら中のファイルにも同じルールを適用するか決める |
| 実装 | ① 拡張子を allowlist で照合 ② 先頭のマジックバイトや専用ライブラリ（Pillow、pdf パーサなど）で中身を判定 ③ 両者が一致しなければ拒否。画像は再エンコード（再書き出し）してメタデータや末尾の余計なデータを落とすと効果的 |
| レビュー | `mimetype`・`content_type`・`getContentType()` だけで判定している箇所、`endswith(".jpg")` のような単純比較、拡張子 denylist（`.php` だけ禁止など）を探す |
| テスト | PHP スクリプトを `avatar.jpg` に改名して送る → 拒否。PNG を `x.pdf` に改名 → 拒否。`Content-Type: image/png` を付けたテキスト → 拒否。`photo.JPG`・`a.jpg.php`・`a.php.jpg` など拡張子の大小・二重拡張子も試す |

**誤解しやすいポイント**: 「マジックバイトを確認したから安全」も十分ではありません。先頭だけ正しい画像で後ろにスクリプトを付けた **polyglot ファイル** はマジックバイト検査を通ります。だからこそ原文は「画像の再書き出し」や「専用ライブラリでの検証」も挙げています。逆に「Pillow で開けた」だけで拡張子を見ていないと、`shell.php` という名前の正しい画像が保存されることがあり、V5.3.1 と組み合わさると危険です。

```python
# ✅ 拡張子 allowlist + 中身の判定 + 再書き出し（Pillow）
ALLOWED = {".jpg": "JPEG", ".jpeg": "JPEG", ".png": "PNG"}
ext = Path(upload.filename).suffix.lower()
if ext not in ALLOWED:
    raise ValidationError("unsupported extension")
img = Image.open(upload.stream)
if img.format != ALLOWED[ext]:
    raise ValidationError("content does not match extension")
img.save(out_path, format=ALLOWED[ext])   # 再書き出し
```

### V5.3.1 アップロードファイルをサーバー側コードとして実行させない `L1`

> **原文**: Verify that files uploaded or generated by untrusted input and stored in a public folder, are not executed as server-side program code when accessed directly with an HTTP request.

**ひとことで**: 公開ディレクトリに置いたアップロードファイルや生成ファイルが、URL で直接叩かれてもサーバーで実行されないようにする。

**開発の現場で言うと**: PHP + Apache、Java の JSP、ASP.NET のように「ドキュメントルート配下の特定拡張子のファイルを実行する」構成で特に問題になります。`/public/uploads/shell.php` が置かれて実行されれば Web シェルです。
「アップロード」だけでなく「**信頼できない入力から生成されたファイル**」も対象です。例えばユーザー入力からテンプレートやエクスポートファイルを生成して公開フォルダに書き出す処理も含まれます。
Django / Rails / Express / Next.js のように、アプリがリクエストをルーティングし、静的ファイル配信はコードを実行しない構成では、この攻撃は起きにくい傾向があります。ただし Rails の `public/`・Next.js の `public/`・Express の `express.static` に書き込むと**誰でも直接取得できる**ようになるので、別の問題（V5.2.2 や XSS）を招きます。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 保存先はドキュメントルートの外かオブジェクトストレージ（S3 など）にし、配信はアプリ経由か署名付き URL にする方針を決める |
| 実装 | どうしても公開ディレクトリに置くなら、そのディレクトリでスクリプト実行を無効化（nginx / Apache の設定）。保存名はサーバー生成にして実行可能な拡張子を付けない。Apache なら `.htaccess` のアップロードも禁止する |
| レビュー | 保存先パスに `public/`・`webroot`・`htdocs`・`static/` が含まれていないか。Web サーバー設定でアップロードディレクトリに `php`/`jsp` ハンドラが効いていないか |
| テスト | `<?php echo 1+1; ?>` を含むファイルを `.php`・`.phtml`・`.php5` などの名前でアップロードし、返された URL にアクセスして `2` が表示されない（実行されない）こと。`.htaccess` のアップロードが拒否されること |

**誤解しやすいポイント**: 「拡張子チェックで `.php` を禁止したから大丈夫」は不十分です。`.phtml`・`.pht` など別の拡張子が実行対象になっている設定や、`.htaccess` で任意の拡張子を実行可能にされる手口があります。拡張子チェックは V5.2.2 の役割で、V5.3.1 は「**仮に変なファイルが置かれても実行されない**」ための多層防御だと考えてください。

### V5.3.2 ファイルパスにユーザー提供の名前を使わない `L1`

> **原文**: Verify that when the application creates file paths for file operations, instead of user-submitted filenames, it uses internally generated or trusted data, or if user-submitted filenames or file metadata must be used, strict validation and sanitization must be applied. This is to protect against path traversal, local or remote file inclusion (LFI, RFI), and server-side request forgery (SSRF) attacks.

**ひとことで**: ファイルを開く・保存する・削除するパスは、サーバーが生成した ID などから組み立て、ユーザーが送った名前は使わない（使うなら厳密に検証する）。

**開発の現場で言うと**: アップロード時の保存名だけでなく、「`/download?file=report-2024.pdf` で帳票を返す」「`?template=invoice` でテンプレートを切り替える」「`?lang=ja` で言語ファイルを読む」といった**読み込み側**でも頻出します。zip 内のエントリ名やファイルのメタデータ（EXIF など）も「ユーザー提供」です。
フレームワークの補助はありますが範囲は限定的です。例えば Werkzeug の `secure_filename()`、Django のストレージ API のパス検証、Express の `res.sendFile()` の `root` オプションなどはトラバーサル対策を持ちますが、`open()`・`fs.readFile()`・`File.new` を直接使う場合は自分で守る必要があります。
原文が SSRF・RFI を挙げているのは、パスのつもりの値が URL として解釈されることがあるためです（例: PHP の `include` / `file_get_contents` は設定次第で `http://` を受け付ける、画像処理ライブラリが URL を読みに行くなど）。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | 保存名は UUID などサーバー生成にし、元のファイル名は DB に「表示用の文字列」としてだけ持つ。ダウンロードは `?file=名前` ではなく `/files/{id}` にして DB で引く |
| 実装 | どうしてもユーザー由来の名前を使うなら、allowlist（`^[A-Za-z0-9_-]{1,64}$` など）で検証し、正規化後のパスが基準ディレクトリ配下にあることを確認する。スキーム（`http:` など）を含む値は拒否 |
| レビュー | `os.path.join(BASE, user_input)`、`path.join`/`path.resolve` + `req.query`/`req.params`、`File.join`/`Rails.root.join(params[...])`、`new File(base, param)`、PHP の `include $_GET[...]` を grep。`file.originalname`/`filename` がパスに入っていないか |
| テスト | `../../etc/passwd`、`..%2f..%2fetc%2fpasswd`、`....//`、`/etc/passwd`（絶対パス）、Windows なら `..\\`、`C:\\`、URL（`http://169.254.169.254/`、`file:///etc/passwd`）を渡し、いずれも拒否されるか基準ディレクトリ外に出ないこと |

**誤解しやすいポイント**: 「`../` を空文字に置換している」は典型的な不十分対策です。`....//` は置換後に `../` になります。また Python の `os.path.join("/uploads", "/etc/passwd")` は**第 2 引数が絶対パスだと第 1 引数を捨てる**ため、`..` を含まなくても外に出られます。置換や denylist ではなく、「サーバー生成の名前を使う」か「正規化後に基準ディレクトリ配下か確かめる」で対処します。

```python
# ✅ どうしてもユーザー由来の名前を使う場合の最終チェック
base = Path(UPLOAD_DIR).resolve()
target = (base / user_name).resolve()
if not target.is_relative_to(base):   # Python 3.9+
    raise PermissionError("path traversal")
```

## この章のまとめ: PR レビューで聞く質問

- このアップロード機能の上限サイズはいくつで、プロキシ・アプリ・ライブラリのどの層で強制していますか？
- ファイル形式の判定に、クライアント申告の `Content-Type` や拡張子だけを使っていませんか？ 中身（マジックバイト・専用ライブラリ・再書き出し）でも確認していますか？
- アップロードしたファイルの保存先は公開ディレクトリの外ですか？ 公開ディレクトリなら、そこでスクリプトが実行されない設定になっていますか？
- ファイルパスの組み立てにユーザーが送った名前・パラメータ・zip のエントリ名を使っていませんか？
- 拡張子を偽ったファイルや `../` を含む名前を送るテストケースがありますか？
