# V13 設定 — L1 要件を開発の観点で読む

> 対象: L1 要件 1 件 ／ 章の解説: [../chapters/V13-configuration.md](../chapters/V13-configuration.md)

## この章の要件を一言でいうと

アプリを **ビルドしてデプロイするとき** の設定の話です。コードの中身よりも、Dockerfile、`.dockerignore`、CI/CD のデプロイスクリプト、Web サーバーの公開ディレクトリ設定に現れます。
L1 は 1 件だけで、「`.git` などのソース管理メタデータを本番に持ち込まない（または絶対にアクセスできないようにする）」です。
地味に見えますが、`.git` が公開されているとソースコード全体・コミット履歴・過去にコミットしてしまったシークレットまで復元されることがあり、他の脆弱性を探す足がかりにもなります。

## 要件ごとの読み解き

### V13.4.1 ソース管理のメタデータをデプロイしない `L1`

> **原文**: Verify that the application is deployed either without any source control metadata, including the .git or .svn folders, or in a way that these folders are inaccessible both externally and to the application itself.

**ひとことで**: `.git` や `.svn` フォルダを含めずにデプロイするか、含める場合は外部からもアプリ自身からもアクセスできないようにする。

**開発の現場で言うと**: よくある崩れ方は次のような場面です。

- サーバーに SSH して `git pull` でデプロイしており、ドキュメントルートがリポジトリのルートになっている（PHP や静的サイトで多い）。
- Dockerfile で `COPY . .` しているが `.dockerignore` に `.git` が無い。
- 静的サイト（SPA のビルド成果物など）を S3 やオブジェクトストレージにリポジトリごと同期している。
- アプリが実行時に `.git/HEAD` を読んでバージョン表示している（=アプリ自身からアクセスできる状態）。

Django / Rails / Spring Boot / Express などのアプリサーバーは、通常はルーティングに定義したパスとフレームワーク側で指定した静的ファイルディレクトリだけを配信するので、`.git` がそのまま URL で見えることは比較的少ないです。危ないのは、**前段の nginx / Apache がプロジェクトのルートを丸ごと公開している**場合や、`express.static(__dirname)` のようにリポジトリのルートを静的配信ディレクトリにしている場合です。
要件は「外部から」だけでなく「アプリ自身から」もアクセスできないことを求めています。つまり「nginx で `/.git` を 403 にしたから OK」ではなく、**成果物に `.git` を含めない** のが基本線です。コミットハッシュをアプリで表示したいなら、ビルド時に環境変数やファイルとして埋め込みます。

| 観点 | 具体的にやること |
| --- | --- |
| 設計 | デプロイ方式を「ビルド成果物（コンテナイメージ、アーカイブ、ビルド済み静的ファイル）を配布する」形にし、本番サーバーで `git pull` しない。バージョン情報はビルド時に `GIT_SHA` などの環境変数として注入する方針にする。 |
| 実装 | `.dockerignore` に `.git`、`.svn`、`.hg` などを入れる。マルチステージビルドで、最終イメージには必要なファイルだけを `COPY` する。静的ホスティングへの同期はビルド出力ディレクトリ（`dist/` など）だけを対象にする。多層防御として Web サーバーでドットで始まるパスへのアクセスを拒否する。 |
| レビュー | Dockerfile の `COPY . .`、`.dockerignore` の有無と中身、CI のデプロイスクリプトの `rsync` / `aws s3 sync` / `scp` の対象ディレクトリ、`express.static(` / `root` / `DocumentRoot` の指す場所、コード内の `.git/` という文字列を確認する。 |
| テスト | `curl -i https://example.com/.git/HEAD` と `curl -i https://example.com/.git/config`、`/.svn/entries`、`/.svn/wc.db` が 404（または 403）になること（200 で `ref: refs/heads/...` が返ったら不合格）。コンテナでは `docker run --rm <image> ls -la /app` などで `.git` が含まれていないことを CI で確認する。 |

**誤解しやすいポイント**:
- 「`/.git/` にアクセスしたらディレクトリ一覧が出なかった（403 だった）から大丈夫」は誤りです。ディレクトリ一覧が無効でも、`/.git/HEAD` や `/.git/objects/...` のような **個別ファイル** は取得でき、既知のファイル名をたどれば履歴を復元するツールが存在します。テストは必ず個別ファイルで行ってください。
- 「`.gitignore` に書いてあるから大丈夫」も誤りです。`.gitignore` は Git に追跡させないファイルの指定で、`.git` フォルダそのもののデプロイとは関係ありません。

```dockerfile
# .dockerignore
.git
.svn
.env
```

## この章のまとめ: PR レビューで聞く質問

- デプロイ成果物（イメージ・アーカイブ・同期対象）に `.git` / `.svn` が含まれない構成になっていますか？
- `.dockerignore` はありますか？ `COPY . .` の対象から `.git` は除外されていますか？
- Web サーバーやフレームワークの静的配信ディレクトリが、リポジトリのルートを指していませんか？
- アプリがバージョン表示などのために実行時に `.git` を読んでいませんか？ ビルド時注入に置き換えられますか？
- 本番 URL に対して `/.git/HEAD` と `/.git/config` が取得できないことを、デプロイ後の確認や定期チェックに含めていますか？
