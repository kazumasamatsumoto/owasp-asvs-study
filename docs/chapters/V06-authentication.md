# V6 認証（Authentication）

> 📘 原文: [0x15-V6-Authentication.md](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)
> 📊 要件数: **47**（L1: 13 / L2: 22 / L3: 12）
> ✅ 全要件のチェックリスト: [checklists/by-chapter/V6.md](../../checklists/by-chapter/V6.md)

## 1. この章の目的

認証とは、個人やデバイスが本物であることを確立・確認するプロセスです。この章は、なりすましへの耐性を確保し、パスワードの回収や盗聴を防ぐことを目的としています。
要件の多くは NIST SP 800-63B（認証とライフサイクル管理）を土台にしていますが、標準を網羅するのではなく、よくある脅威とよく悪用される認証の弱点に焦点を当てています。
パスワードポリシー、総当たり・クレデンシャルスタッフィング対策、多要素認証（MFA）、認証要素の登録・回復、外部 ID プロバイダ（IdP）連携までを扱います。
レベルごとの期待値がはっきりしているのも特徴で、**L2 では MFA の強制**、**L3 ではハードウェアベースの（フィッシング耐性のある）認証**が求められます。
なお、リスクに応じて認証段階を変える「適応型認証」は認可の判断とも関わるため、「認可（V8）」の章で扱われます。パスワードの保存方式（ハッシュ化）は「暗号（V11）」の章（V11.4.2）にあります。

## 3. 押さえるべき重要要件

### V6.2.1 / V6.2.5 / V6.2.9 — 長さを重視し、文字種ルールを課さない（L1 / L2）

- **要件（意訳）**:
  - 6.2.1（L1）: ユーザーが設定するパスワードは最低 8 文字。ただし最低 15 文字が強く推奨される。
  - 6.2.5（L1）: どんな構成のパスワードも使えること。使える文字の種類を制限するルールは設けない。大文字・小文字・数字・記号の最低数を要求してはならない。
  - 6.2.9（L2）: 少なくとも 64 文字のパスワードを許可すること。
- **なぜ重要か**: 「大文字・数字・記号を各 1 文字以上」といったルールは、`Password1!` のような予測しやすいパターンを生むだけで強度はあまり上がりません。一方で長さの上限が短いと、パスフレーズやパスワードマネージャの長いランダム文字列が使えません。
- **実装のポイント**: 長さ（最小 8、推奨 15、最大は 64 以上）だけを制約にし、強度は次の V6.2.4 / V6.2.12 の禁止リストで担保する。

```python
# ❌ NG 例: 文字種ルールと短い上限
def is_valid(pw):
    return (8 <= len(pw) <= 16
            and re.search(r"[A-Z]", pw) and re.search(r"\d", pw)
            and re.search(r"[!@#$%]", pw))

# ✅ OK 例: 長さ中心 + 禁止リスト
MIN_LEN, MAX_LEN = 15, 128
def is_valid(pw):
    return MIN_LEN <= len(pw) <= MAX_LEN and not is_common_or_breached(pw)
```

### V6.2.4 / V6.2.12 — よく使われるパスワード・漏洩済みパスワードを拒否する（L1 / L2）

- **要件（意訳）**:
  - 6.2.4（L1）: アカウント登録時やパスワード変更時に、アプリのパスワードポリシー（最小長など）に合致する、少なくとも上位 3000 件のよく使われるパスワードのセットと照合すること。
  - 6.2.12（L2）: 登録時・変更時に、漏洩済みパスワードのセットと照合すること。
- **なぜ重要か**: 攻撃者はまず「よくあるパスワード」と「過去に漏洩したパスワード」から試します（パスワードスプレー、クレデンシャルスタッフィング）。これらを最初から使えなくするのが効果的です。
- **実装のポイント**: 上位パスワードのリストはアプリに同梱して照合する。漏洩パスワードは Have I Been Pwned の Pwned Passwords API のように、ハッシュの先頭 5 文字だけを送る k-匿名性方式を使えば、パスワード自体を外部に送らずに済む。

```python
import hashlib, requests

def is_breached(pw: str) -> bool:
    sha1 = hashlib.sha1(pw.encode()).hexdigest().upper()
    prefix, suffix = sha1[:5], sha1[5:]
    r = requests.get(f"https://api.pwnedpasswords.com/range/{prefix}", timeout=5)
    return any(line.split(":")[0] == suffix for line in r.text.splitlines())
```

### V6.2.8 — 受け取ったパスワードをそのまま検証する（L1）

- **要件（意訳）**: 切り詰めや大文字小文字の変換などの加工をせずに、ユーザーから受け取ったとおりのパスワードで検証すること。
- **なぜ重要か**: 先頭 8 文字だけで比較したり、小文字化してから比較したりすると、実質的なパスワードの強度が大きく落ちます。
- **実装のポイント**: `strip()` や `lower()` をかけない。bcrypt のように入力長に上限（72 バイト）があるアルゴリズムでは、黙って切り詰められることに注意する（長いパスワードを許可する V6.2.9 との兼ね合いで、上限のないアルゴリズムを選ぶなどの対応が必要）。

```python
# ❌ NG 例
check(password.strip().lower()[:16], stored_hash)

# ✅ OK 例
check(password, stored_hash)
```

### V6.3.1 / V6.1.1 — 総当たり・クレデンシャルスタッフィング対策を設計どおりに実装する（L1）

- **要件（意訳）**:
  - 6.1.1（L1）: レート制限、自動化対策、適応型応答などの制御を、クレデンシャルスタッフィングやパスワード総当たりへの防御にどう使うかを文書化すること。その設定方法と、悪意のあるアカウントロックアウトをどう防ぐかも明記すること。
  - 6.3.1（L1）: クレデンシャルスタッフィングやパスワード総当たりを防ぐ制御を、そのセキュリティ文書に従って実装すること。
- **なぜ重要か**: 対策がないと、漏洩したID/パスワードの組を大量に試されて、パスワードを使い回しているユーザーのアカウントが次々に乗っ取られます。逆に「5 回失敗で永久ロック」のような単純な対策だと、攻撃者が他人のアカウントをわざとロックできてしまいます。
- **実装のポイント**: アカウント単位と IP 単位の両方でレート制限をかけ、段階的な遅延や CAPTCHA を組み合わせる。ロックは一時的にし、正規ユーザーが回復できる経路を用意する。

```python
# ✅ OK 例: アカウント単位と IP 単位の両方で失敗回数を数える（Redis）
def too_many_attempts(username, ip):
    k_user, k_ip = f"fail:u:{username}", f"fail:ip:{ip}"
    return int(r.get(k_user) or 0) >= 10 or int(r.get(k_ip) or 0) >= 100

def record_failure(username, ip):
    for k, ttl in ((f"fail:u:{username}", 900), (f"fail:ip:{ip}", 3600)):
        r.incr(k); r.expire(k, ttl)
```

### V6.3.3 — L2 以上では多要素認証を必須にする（L2）

- **要件（意訳）**: アプリへのアクセスには、多要素認証メカニズム、または単一要素認証メカニズムの組み合わせを使うこと。L3 では、そのうち 1 つがハードウェアベースの認証メカニズムで、フィッシング攻撃に対する侵害・なりすまし耐性を持ち、ユーザー自身の操作（FIDO ハードウェアキーやスマートフォンのボタン押下など）で認証の意思を確認するものであること。これらを緩める場合は、完全に文書化された根拠と包括的な緩和策が必要。
- **なぜ重要か**: パスワードは漏洩・使い回し・フィッシングで簡単に破られます。2 つ目の要素があれば、パスワードが漏れても即座に乗っ取られることはありません。
- **実装のポイント**: TOTP やパスキー（WebAuthn）などを提供する。なお原文は、メールは認証メカニズムとして許容されないとする NIST の見解に触れており、L3 ではメールを単一要素にも多要素にも使わないこと（V6.3.6）が求められます。

### V6.3.8 — 失敗時の応答からユーザーの存在を推測させない（L3）

- **要件（意訳）**: 失敗した認証チャレンジから、エラーメッセージ・HTTP レスポンスコード・応答時間の違いなどによって有効なユーザーを推測できないこと。登録機能やパスワード忘れ機能にも同じ保護が必要。
- **なぜ重要か**: 「そのユーザーは存在しません」「パスワードが違います」と出し分けると、攻撃者は有効なアカウント一覧を作ってから集中攻撃できます。

```python
# ❌ NG 例: メッセージとタイミングで存在がわかる
user = db.find(username)
if not user:
    return "ユーザーが存在しません", 404
if not verify(password, user.pw_hash):
    return "パスワードが違います", 401

# ✅ OK 例: 同じメッセージ・同じステータス、ユーザー不在でもハッシュ検証を実行
DUMMY_HASH = ph.hash("dummy-password")
user = db.find(username)
ok = verify(password, user.pw_hash if user else DUMMY_HASH) and user is not None
if not ok:
    return "ユーザー名またはパスワードが正しくありません", 401
```

### V6.4.2 / V6.4.3 — 秘密の質問を使わず、MFA を迂回しないリセット手順にする（L1 / L2）

- **要件（意訳）**:
  - 6.4.2（L1）: パスワードのヒントや知識ベース認証（いわゆる「秘密の質問」）が存在しないこと。
  - 6.4.3（L2）: 忘れたパスワードをリセットする安全なプロセスを実装し、そのプロセスが有効になっている多要素認証を迂回しないこと。
- **なぜ重要か**: 「母親の旧姓」「出身地」は SNS などから調べられることが多く、推測も容易です。また、パスワードリセットで MFA が要求されないと、メールを乗っ取るだけで MFA をすり抜けてアカウントを奪えてしまいます。
- **実装のポイント**: リセット用リンクの後でも、登録済みの 2 要素目での確認を求める。

### V6.5.1 / V6.5.5 — ワンタイムコードは一度きり・短命に（L2）

- **要件（意訳）**:
  - 6.5.1: ルックアップシークレット（リカバリーコードなど）、帯域外認証のリクエストやコード、TOTP は、一度しか成功しないこと。
  - 6.5.5: 帯域外認証のリクエスト・コード・トークンと TOTP には有効期限を定めること。帯域外リクエストは最大 10 分、TOTP は最大 30 秒。
- **なぜ重要か**: 使用済みのコードを再利用できると、盗み見やフィッシングで得たコードを攻撃者が後から使えます。

```python
import pyotp

# ❌ NG 例: 同じコードを何度でも通す
def verify_totp(user, code):
    return pyotp.TOTP(user.totp_secret).verify(code)

# ✅ OK 例: 最後に受理したタイムステップを記録し、同じ/過去のステップを拒否
def verify_totp(user, code):
    totp = pyotp.TOTP(user.totp_secret)  # interval=30 秒（デフォルト）
    step = totp.timecode(datetime.now(timezone.utc))
    if step <= (user.last_totp_step or -1):
        return False
    if not totp.verify(code):
        return False
    user.last_totp_step = step
    return True
```

### V6.8.1 / V6.8.2 — 外部 IdP 連携ではユーザー ID の名前空間と署名を確認する（L2）

- **要件（意訳）**:
  - 6.8.1: 複数の IdP をサポートする場合、別の IdP 経由でユーザー ID を偽装できないこと（例: 同じユーザー識別子を使う）。標準的な対策は、IdP の ID（名前空間として機能）と IdP 内のユーザー ID の組み合わせでユーザーを登録・識別すること。
  - 6.8.2: 認証アサーション（JWT や SAML アサーションなど）のデジタル署名の存在と正当性を常に検証し、署名がない・無効なアサーションを拒否すること。
- **なぜ重要か**: `sub` やメールアドレスだけで照合すると、攻撃者が自分で管理できる IdP で同じ値を作り、他人のアカウントにログインできてしまいます。署名を検証しなければ、アサーションを自由に偽造できます。

```python
# ❌ NG 例: sub だけでユーザーを特定
user = User.get(external_id=claims["sub"])

# ✅ OK 例: (発行者, sub) の組で特定
user = User.get(idp_issuer=claims["iss"], external_id=claims["sub"])
```

## 4. よくある脆弱性・アンチパターン

- **文字種の複雑性ルールや定期的なパスワード変更の強制**: V6.2.5 は文字種ルールを、V6.2.10 は定期的なパスワード変更の要求を禁じています。漏洩が判明したときやユーザー自身が変更したときに変えれば十分です。
- **パスワード欄で貼り付けを禁止する、パスワードマネージャを妨げる**（V6.2.7 違反）。
- **パスワード変更時に現在のパスワードを要求しない**: セッションを乗っ取った攻撃者がそのままパスワードを変えられます（V6.2.3）。
- **`admin` / `root` / `sa` などのデフォルトアカウントが有効なまま**（V6.3.2）。
- **秘密の質問やパスワードヒント**（V6.4.2）。
- **システムが発行した初期パスワードをずっと使える**: 初期パスワードやアクティベーションコードは安全な乱数で生成し、短時間か初回利用で失効させ、長期のパスワードにしてはいけません（V6.4.1）。
- **管理者がユーザーのパスワードを直接設定できる**: L3 では、管理者はリセット手続きを開始できても、パスワードを選んだり変えたりできてはいけません（V6.4.6）。
- **`random` モジュールで OTP やリカバリーコードを作る**: CSPRNG（Python なら `secrets`）を使います（V6.5.3）。
- **OTP の試行回数を制限しない**: 6 桁なら 100 万通りしかありません（V6.6.3）。プッシュ通知型 MFA を連打してユーザーに承認させる「プッシュ爆撃」にもレート制限が必要です（V6.6.4）。
- **SMS OTP だけを提供する**: L2 では、電話番号を事前に検証し、より強い方法（TOTP など）も提供し、リスクをユーザーに説明する必要があります。L3 では電話・SMS を選択肢にしてはいけません（V6.6.1）。
- **生体認証を単独の認証要素にする**: 生体認証は、所持要素か知識要素と組み合わせた 2 つ目の要素としてだけ使えます（V6.5.7）。
- **ドキュメント化されていない「裏口」ログイン経路**（モバイル用 API、旧ログイン画面など）があり、そこだけ MFA やレート制限が効いていない（V6.1.3, V6.3.4）。
- **OIDC で `acr` / `amr` / `auth_time` を確認せず、IdP 側で MFA が行われたと思い込む**（V6.8.4）。

## 5. 検証（テスト）のヒント

- **文書の確認**: レート制限・自動化対策の設計（V6.1.1）、パスワード禁止語リスト（V6.1.2）、すべての認証経路の一覧（V6.1.3）があるか。
- **パスワードポリシー**: 7 文字 / 8 文字 / 64 文字以上 / 絵文字や空白を含むパスワードで登録できるか。`password123` のような頻出パスワードや既知の漏洩パスワードを拒否するか。
- **パスワードの加工**: 登録したパスワードの大文字小文字を変えたもの、末尾を削ったもの、末尾に文字を足したものでログインできてしまわないか（V6.2.8）。
- **UI**: `type="password"` か、貼り付けやパスワードマネージャの自動入力が使えるか（V6.2.6, V6.2.7）。
- **総当たり**: Burp Suite Intruder などで連続ログインを試し、レート制限やロックがかかるか、それが他人をロックアウトする手段に悪用できないか。
- **ユーザー列挙**: 存在するユーザーと存在しないユーザーで、メッセージ・ステータスコード・応答時間に差がないか。登録画面とパスワード忘れ画面も確認する（V6.3.8）。
- **MFA**: 同じ TOTP / OTP / リカバリーコードを 2 回使えないか、期限切れのコードが通らないか、別のログインセッション向けに発行されたコードが使えないか（V6.5.1, V6.5.5, V6.6.2）。2 要素目の画面を飛ばして認証後の URL に直接アクセスできないか。
- **リセット**: パスワードリセット経由で MFA を迂回できないか（V6.4.3）。
- **IdP 連携**: 署名を外した・改ざんした JWT / SAML アサーションを拒否するか（V6.8.2）、同じ SAML アサーションを再送して拒否されるか（V6.8.3）。
- **コードレビュー**: `random.` による秘密値の生成、パスワードの `lower()` / `strip()`、`verify=False` / `verify_signature: False` のような署名検証の無効化を grep する。

## 6. 確認問題

**Q1.** 次のパスワードポリシーのうち、ASVS 5.0 の V6.2 に違反しているものをすべて選べ。
(a) 最小 8 文字　(b) 英大文字・数字・記号をそれぞれ 1 文字以上含むこと　(c) 90 日ごとに変更を強制　(d) 最大 32 文字

<details><summary>答えと解説</summary>

**(b)、(c)、(d)** が違反です。
- (a) は **V6.2.1**（L1）の最低要件（8 文字以上、15 文字以上を強く推奨）を満たしています。
- (b) は **V6.2.5**（L1）違反。文字種の最低数を要求してはいけません。
- (c) は **V6.2.10**（L2）違反。定期的なパスワード変更を求めてはいけません。
- (d) は **V6.2.9**（L2）違反。少なくとも 64 文字のパスワードを許可する必要があります。

</details>

**Q2.** ログイン失敗時に「このメールアドレスは登録されていません」と表示している。どの要件の観点で問題か。また、他にどの機能で同じ確認が必要か。

<details><summary>答えと解説</summary>

**V6.3.8**（L3）です。エラーメッセージ・HTTP ステータスコード・応答時間の違いから、有効なユーザーを推測できてはいけません。原文は、**登録機能とパスワード忘れ機能**にも同じ保護が必要だとしています。

</details>

**Q3.** TOTP と帯域外（Out-of-Band）認証リクエストの最大有効期限は、それぞれ ASVS ではいくらと定められているか。要件 ID とあわせて答えよ。

<details><summary>答えと解説</summary>

**V6.5.5**（L2）により、帯域外認証リクエストは**最大 10 分**、TOTP は**最大 30 秒**です。あわせて **V6.5.1**（L2）により、これらのコードは一度しか成功してはいけません。

</details>

**Q4.** アプリが Google と自社 IdP の両方でログインできる。ユーザーを ID トークンの `sub` クレームだけで識別している場合の問題点と、ASVS が示す標準的な対策を答えよ。

<details><summary>答えと解説</summary>

別の IdP で同じユーザー識別子を持つアカウントを用意されると、他人になりすまされるおそれがあります。**V6.8.1**（L2）は、IdP の ID（名前空間）と IdP 内のユーザー ID の組み合わせでユーザーを登録・識別することを標準的な対策として挙げています。

</details>

**Q5.** L2 と L3 のアプリでは、それぞれどのような認証が求められるか。V6.3.3 をもとに説明せよ。

<details><summary>答えと解説</summary>

**V6.3.3**（L2）は、アプリへのアクセスに多要素認証（または単一要素認証の組み合わせ）を使うことを求めます。L3 ではさらに、要素の 1 つが**ハードウェアベース**で、フィッシングに対する侵害・なりすまし耐性を持ち、ユーザー自身の操作（FIDO ハードウェアキーやスマートフォンのボタン押下など）で認証の意思を確認するものでなければなりません。これを緩める場合は、完全に文書化された根拠と包括的な緩和策が必要です。

</details>
