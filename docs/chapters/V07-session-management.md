# V7 セッション管理（Session Management）

> 📘 原文: [0x16-V7-Session-Management.md](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)
> 📊 要件数: **19**（L1: 6 / L2: 12 / L3: 1）
> ✅ 全要件のチェックリスト: [checklists/by-chapter/V7.md](../../checklists/by-chapter/V7.md)

## 1. この章の目的

セッション管理は、HTTP のようなステートレスなプロトコルの上で、ユーザーやデバイスとのやり取りを時間を通して関連付けるための仕組みです。現代のアプリでは、性質や目的の異なる複数のセッショントークンを使うこともあります。
安全なセッション管理とは、攻撃者が被害者のセッションを入手・利用・悪用できないようにするものです。原文は高レベルの要件として、「セッションは個人ごとに一意で、推測も共有もできないこと」「不要になったら無効化され、無操作の期間が続けばタイムアウトすること」の 2 点を挙げています。
多くの要件は NIST SP 800-63 の一部の管理策に基づいています。
なお、Cookie の属性に関する要件は「Web フロントエンドセキュリティ（V3）」、JWT などの自己完結型トークンの要件は「自己完結型トークン（V9）」の章にあります。

## 3. 押さえるべき重要要件

### V7.2.1 — セッショントークンは信頼できるバックエンドで検証する（L1）

- **要件（意訳）**: セッショントークンの検証はすべて、信頼できるバックエンドサービスで行うこと。
- **なぜ重要か**: フロントエンドの JavaScript だけで「ログイン済みか」を判定していると、ブラウザの開発者ツールで簡単に書き換えられます。API 側でトークンを検証していなければ、誰でもデータを取得できます。
- **実装のポイント**: すべての保護対象 API で、サーバー側のミドルウェアやデコレータがトークンを検証する。クライアント側の判定は UI 表示の切り替えにとどめる。

```python
# ❌ NG 例: クライアントが送ってきた「ログイン済み」フラグを信じる
@app.get("/api/orders")
def orders():
    if request.headers.get("X-Logged-In") == "true":
        return get_orders(request.args["user_id"])

# ✅ OK 例: サーバー側でセッションを検証し、ユーザーもセッションから取得
@app.get("/api/orders")
@login_required
def orders():
    return get_orders(current_user.id)
```

### V7.2.2 / V7.2.3 — 動的に生成した、十分にランダムなトークンを使う（L1）

- **要件（意訳）**:
  - 7.2.2: セッション管理には、動的に生成された自己完結型トークンまたは参照トークンを使うこと。つまり、静的な API シークレットやキーを使わないこと。
  - 7.2.3: ユーザーセッションを参照トークンで表す場合、トークンは一意で、暗号論的に安全な疑似乱数生成器（CSPRNG）で生成され、少なくとも 128 ビットのエントロピーを持つこと。
- **なぜ重要か**: 固定の API キーをセッション代わりに使うと、漏れたら無期限に使われ、ユーザーごとの終了もできません。連番・時刻・`random` モジュールで作ったトークンは推測されます。
- **実装のポイント**: 自作せず、フレームワークのセッション機構を使うのが基本。自作する場合は `secrets` を使う。

```python
import random, secrets, time

# ❌ NG 例: 予測可能なトークン
token = f"{user_id}-{int(time.time())}"
token = str(random.getrandbits(64))

# ✅ OK 例: CSPRNG で 256 ビット（32 バイト）
token = secrets.token_urlsafe(32)
```

### V7.2.4 — 認証時（再認証時も）にセッショントークンを新しくする（L1）

- **要件（意訳）**: ユーザー認証時（再認証を含む）に新しいセッショントークンを生成し、現在のセッショントークンを終了させること。
- **なぜ重要か**: ログイン前後で同じセッション ID を使い続けると、攻撃者があらかじめ用意したセッション ID を被害者に使わせ、被害者がログインした後にそのセッションを乗っ取れます（セッション固定攻撃）。
- **実装のポイント**: ログイン成功時に古いセッションを破棄して新しい ID を発行する。

```python
# ❌ NG 例: 既存セッションにユーザー ID を書き込むだけ
session["user_id"] = user.id

# ✅ OK 例（Django）: ログイン時に ID を再生成
from django.contrib.auth import login
login(request, user)        # 内部で cycle_key() により ID を再生成

# 自前のセッションストアの場合
old = request.cookies.get("sid")
store.delete(old)
sid = secrets.token_urlsafe(32)
store.set(sid, {"user_id": user.id})
```

### V7.3.1 / V7.3.2 — 無操作タイムアウトと絶対的な有効期限（L2）

- **要件（意訳）**:
  - 7.3.1: リスク分析と文書化されたセキュリティ上の判断に従って再認証を強制する、無操作タイムアウトがあること。
  - 7.3.2: 同様に、再認証を強制する絶対的な最大セッション有効期間があること。
- **なぜ重要か**: 共有 PC での放置や、盗まれたトークンが長く使える状態は、乗っ取りのチャンスを広げます。操作し続ける限り延長され続けるだけのセッションだと、盗まれたトークンを使い続けられます。
- **実装のポイント**: 「最終操作時刻」と「ログイン時刻」の 2 つを持ち、両方をチェックする。値そのものは V7.1.1 に従って文書化する（ASVS は具体的な時間を定めていない）。

```python
IDLE_TIMEOUT = timedelta(minutes=30)     # 値は文書化したリスク分析に基づき決める
ABSOLUTE_TIMEOUT = timedelta(hours=12)

def check_session(s):
    now = datetime.now(timezone.utc)
    if now - s["last_seen"] > IDLE_TIMEOUT or now - s["created_at"] > ABSOLUTE_TIMEOUT:
        destroy(s)
        raise ReauthenticationRequired()
    s["last_seen"] = now
```

### V7.4.1 — セッション終了後は二度と使えないようにする（L1）

- **要件（意訳）**: セッションの終了（ログアウトや期限切れなど）が発生したら、それ以降のセッション利用を許さないこと。参照トークンやステートフルなセッションでは、バックエンドのセッションデータを無効化することを意味する。自己完結型トークンを使う場合は、終了済みトークンのリストを保持する、ユーザーごとの日時より前に発行されたトークンを拒否する、ユーザーごとの署名鍵をローテーションする、などの仕組みが必要。
- **なぜ重要か**: ログアウトしても Cookie を消すだけでサーバー側のセッションが生きていると、盗まれたトークンはそのまま使えます。JWT は有効期限まで有効なので、何もしなければログアウトの意味がありません。

```python
# ❌ NG 例: Cookie を消すだけ
resp.delete_cookie("sid")

# ✅ OK 例: サーバー側のセッションも破棄
store.delete(request.cookies["sid"])
resp.delete_cookie("sid")

# ✅ OK 例（JWT）: ユーザーごとの「この時刻より前の発行は無効」
if claims["iat"] < user.tokens_valid_after.timestamp():
    raise Unauthorized()
```

### V7.4.2 / V7.4.3 — アカウント無効化時・認証要素変更時のセッション終了（L1 / L2）

- **要件（意訳）**:
  - 7.4.2（L1）: ユーザーアカウントが無効化または削除されたとき（退職者など）、すべてのアクティブセッションを終了すること。
  - 7.4.3（L2）: 認証要素の変更・削除に成功した後（リセットや回復によるパスワード変更、MFA 設定の更新を含む）、他のすべてのアクティブセッションを終了する選択肢をユーザーに提供すること。
- **なぜ重要か**: 退職者のアカウントを無効化しても既存のセッションが生きていれば、アクセスを続けられます。パスワードが漏れたと気づいて変更しても、攻撃者のセッションが残っていれば意味がありません。
- **実装のポイント**: ユーザー ID からそのユーザーの全セッションを引けるようにしておく（例: Redis でユーザーごとのセッション ID 集合を持つ）。

### V7.5.1 — 重要なアカウント属性の変更前に完全な再認証を求める（L2）

- **要件（意訳）**: メールアドレス、電話番号、MFA 設定、その他アカウント回復に使われる情報など、認証に影響しうる重要なアカウント属性を変更する前に、完全な再認証を求めること。
- **なぜ重要か**: 一時的にセッションを奪った攻撃者（XSS、放置された PC など）がメールアドレスを自分のものに変えれば、パスワードリセットでアカウントを恒久的に奪えます。
- **実装のポイント**: 直近の認証時刻をセッションに持ち、重要操作の直前に再認証させる。

```python
# ✅ OK 例
@app.post("/account/email")
@login_required
def change_email():
    if not recently_reauthenticated(session, within=timedelta(minutes=5)):
        return redirect(url_for("reauth", next=request.path))
    ...
```

### V7.6.2 — ユーザーの操作なしにセッションを作らない（L2）

- **要件（意訳）**: セッションの作成には、ユーザーの同意または明示的な操作のどちらかが必要であること。ユーザーの関与なしに新しいアプリケーションセッションが作られるのを防ぐ。
- **なぜ重要か**: SSO で IdP 側にログイン済みだと、攻撃者のページに埋め込まれたリンクや iframe から、ユーザーが気づかないうちに RP 側のセッションが作られることがあります。
- **実装のポイント**: SSO ログインはユーザーが「ログイン」ボタンを押したときだけ開始する、など明示的な操作を起点にする。

## 4. よくある脆弱性・アンチパターン

- **ログイン後もセッション ID を変えない**（セッション固定, V7.2.4）。
- **ログアウトでサーバー側のセッションを破棄しない / JWT を失効させる仕組みがない**（V7.4.1）。
- **固定の API キーをユーザーセッションの代わりに使う**（V7.2.2）。
- **自作トークンを `random`、連番、時刻、ユーザー ID のハッシュなどで生成する**（V7.2.3）。
- **フロントエンドだけでログイン状態を判定し、API 側で検証しない**（V7.2.1）。
- **タイムアウトがない、または操作し続ける限り無限に延長される**（V7.3.1, V7.3.2）。
- **アカウントを無効化・削除しても既存セッションが生き続ける**（V7.4.2）。
- **ログアウトボタンが見つけにくい、一部のページにしかない**（V7.4.4）。
- **管理者が特定ユーザー（または全ユーザー）のセッションを強制終了できない**: インシデント対応時に困ります（V7.4.5）。
- **メールアドレスや MFA 設定を、現在のセッションだけで変更できる**（V7.5.1）。
- **送金など特に重要な取引を追加の認証なしで実行できる**（V7.5.3, L3）。
- **同時セッション数の方針や、SSO と自アプリのセッション期間の関係が決まっていない**（V7.1.2, V7.1.3）。

## 5. 検証（テスト）のヒント

- **文書の確認**: 無操作タイムアウトと絶対的な最大有効期間、NIST SP 800-63B の再認証要件から外れる場合はその理由（V7.1.1）、同時セッション数の上限と上限到達時の挙動（V7.1.2）、SSO などフェデレーション環境でのセッション連携（V7.1.3）が書かれているか。
- **トークンの品質**: 多数のセッショントークンを収集し、Burp Suite Sequencer などでランダム性を評価する。トークンの長さから 128 ビット以上のエントロピーがありそうか。
- **セッション固定**: ログイン前のセッション ID を控え、ログイン後に変わっているか（V7.2.4）。再認証の後も変わるか。
- **ログアウト**: ログアウト前のトークンを控えておき、ログアウト後にそのトークンで API を叩いて拒否されるか（V7.4.1）。
- **タイムアウト**: 無操作で放置した後、および操作し続けて最大有効期間を超えた後に、再認証を求められるか（V7.3.1, V7.3.2）。
- **アカウント無効化**: ログイン中のユーザーを管理画面から無効化し、そのセッションが即座に使えなくなるか（V7.4.2）。
- **パスワード変更**: 2 つのブラウザでログインし、片方でパスワードを変更したとき、もう片方のセッションを終了する選択肢が提示されるか（V7.4.3）。
- **再認証**: メールアドレス・電話番号・MFA 設定の変更時に再認証を求められるか（V7.5.1）。
- **セッション一覧**: ユーザーが自分のアクティブセッションを一覧でき、少なくとも 1 要素で再認証したうえで終了できるか（V7.5.2）。
- **サーバー側検証**: Cookie や `Authorization` ヘッダを外して/改ざんして API を直接呼び、拒否されるか（V7.2.1）。
- 参考: OWASP WSTG の Session Management Testing の各テスト項目。

## 6. 確認問題

**Q1.** ログインの前後でセッション ID が同じままになっている。この状態で成立する攻撃名と、違反している要件 ID を答えよ。

<details><summary>答えと解説</summary>

**セッション固定攻撃**です。違反しているのは **V7.2.4**（L1）で、ユーザー認証時（再認証を含む）に新しいセッショントークンを生成し、現在のトークンを終了させることを求めています。

</details>

**Q2.** 参照トークン（ランダムなセッション ID）をセッションに使う場合、V7.2.3 が求める条件を 3 つ挙げよ。

<details><summary>答えと解説</summary>

**V7.2.3**（L1）は、(1) 一意であること、(2) CSPRNG（暗号論的に安全な疑似乱数生成器）で生成されること、(3) 少なくとも 128 ビットのエントロピーを持つこと、を求めています。Python なら `secrets.token_urlsafe(32)` などを使います。

</details>

**Q3.** JWT（自己完結型トークン）でセッションを管理している。ログアウト後にトークンを使えなくするために、V7.4.1 が例示している方法を 1 つ以上答えよ。

<details><summary>答えと解説</summary>

**V7.4.1**（L1）は次の方法を例示しています。
- 終了したトークンのリストを保持する
- ユーザーごとの日時より前に発行されたトークンを拒否する
- ユーザーごとの署名鍵をローテーションする

自己完結型トークンは有効期限まで有効なままになるため、こうした追加の仕組みが必要です。

</details>

**Q4.** 次のうち、V7.3 が L2 で求めているタイムアウトをすべて選べ。
(a) 無操作タイムアウト　(b) 絶対的な最大セッション有効期間　(c) 30 分ちょうどの固定タイムアウト

<details><summary>答えと解説</summary>

**(a) と (b)** です。**V7.3.1** が無操作タイムアウト、**V7.3.2** が絶対的な最大有効期間を求めています。具体的な時間は ASVS では決めておらず、リスク分析と文書化されたセキュリティ上の判断（**V7.1.1**）に従って決めます。したがって (c) は要件ではありません。

</details>

**Q5.** ユーザーがメールアドレスを変更する機能を作る。V7.5.1 に従うと何が必要か。また、それがない場合にどのような攻撃が考えられるか。

<details><summary>答えと解説</summary>

**V7.5.1**（L2）に従い、変更の前に**完全な再認証**を求める必要があります。メールアドレス・電話番号・MFA 設定・アカウント回復に使う情報など、認証に影響しうる属性が対象です。
再認証がないと、XSS や放置された端末などで一時的にセッションを奪った攻撃者がメールアドレスを自分のものに変え、パスワードリセットを使ってアカウントを恒久的に乗っ取れます。

</details>
