# V16 セキュリティログとエラー処理（Security Logging and Error Handling）

> 📘 原文: [0x25-V16-Security-Logging-and-Error-Handling.md](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md)
> 📊 要件数: **17**（L1: 0 / L2: 16 / L3: 1）
> ✅ 全要件のチェックリスト: [checklists/by-chapter/V16.md](../../checklists/by-chapter/V16.md)

## 1. この章の目的

セキュリティログは、エラーログやパフォーマンスログとは別物です。認証の判断、アクセス制御の判断、入力検証やビジネスロジック検証などのセキュリティ制御を回避しようとする試みといった、セキュリティに関連するイベントを記録するためのものです。その目的は、SIEM などの分析ツール向けに、信号価値の高い構造化データを提供し、検知・対応・調査を支えることにあります。

ログには、法的に必要な場合を除いて機微な個人データを含めるべきではなく、記録したデータは高価値の資産として保護しなければなりません。ログがプライバシーやシステムのセキュリティを損なってはなりません。また、アプリケーションは不要な情報の開示や混乱を避けて、安全に失敗（fail securely）しなければなりません。

この章の要件はすべて L2 以上（L1 要件なし）で、大半が L2 です。

## 3. 押さえるべき重要要件

### V16.2.1 / V16.2.2 — 調査に必要なメタデータと正確なタイムスタンプ（L2）

- **要件（意訳）**: 各ログエントリには、イベント発生時のタイムラインを詳細に調査できるよう必要なメタデータ（いつ・どこで・誰が・何を）を含めること（V16.2.1）。すべてのログ記録コンポーネントの時刻ソースを同期し、セキュリティイベントのメタデータのタイムスタンプは UTC を使うか明示的なタイムゾーンオフセットを含めること。分散システム間の一貫性を保ち、夏時間切り替え時の混乱を防ぐため UTC が推奨される（V16.2.2）。
- **なぜ重要か**: 「誰が」「どの IP から」「何をしたか」が欠けたログでは、インシデント時に被害範囲を特定できません。サーバごとに時刻やタイムゾーンがずれていると、複数システムのログを突き合わせた時系列の再構成ができません。
- **実装のポイント**: NTP などで時刻を同期し、ログは UTC の ISO 8601 形式で出力します。V16.2.4 のとおり、ログ基盤が読み取り・相関できる共通フォーマット（JSON など）にします。

```python
import logging

# ❌ NG 例: 誰が・どこから・いつ（タイムゾーン不明）が分からない
logging.info("login failed")

# ✅ OK 例: UTC タイムスタンプ + 構造化（JSON）+ who/what/where
import json, datetime

def security_log(event, **fields):
    entry = {
        "ts": datetime.datetime.now(datetime.timezone.utc).isoformat(),  # 2026-11-08T03:12:45.123+00:00
        "event": event,
        "app": "web-api",
        **fields,
    }
    logging.getLogger("security").info(json.dumps(entry, ensure_ascii=False))

security_log("authn_login_fail", user="alice", src_ip=client_ip,
             method="password", reason="bad_password", request_id=req_id)
```

### V16.2.5 — 機微データは保護レベルに応じてログに記録する（L2）

- **要件（意訳）**: 機微データをログに記録する場合、アプリケーションはそのデータの保護レベルに基づいてログ記録を制御すること。例えば、認証情報や決済情報などは記録してはならない場合がある。セッショントークンなどのデータは、全体または一部をハッシュ化またはマスクした形でのみ記録してよい場合がある。
- **なぜ重要か**: パスワードやトークンがログに残ると、ログを閲覧できる人（運用者、ログ基盤の利用者、ログが漏えいした場合の攻撃者）がアカウントを乗っ取れます。原文も、機微データを無頓着に記録するとログ自体が機密扱いとなり、暗号化・厳格な保持ポリシー・監査での開示リスクの対象になると注意しています。
- **実装のポイント**: V14.1 のデータ分類に従い、ログ出力時にマスク・ハッシュ化する仕組みを共通化します。

```python
import hashlib

# ❌ NG 例: リクエストを丸ごとログに出す（パスワードやトークンが残る）
logging.info(f"login request: {request.form.to_dict()} headers={dict(request.headers)}")

# ✅ OK 例: パスワードは記録しない。トークンはハッシュの一部のみ
def token_fingerprint(token: str) -> str:
    return hashlib.sha256(token.encode()).hexdigest()[:12]

security_log("session_created", user=user.id,
             session=token_fingerprint(session_token))
```

### V16.3.1 / V16.3.2 — 認証操作と認可の失敗を記録する（L2）

- **要件（意訳）**: 成功・失敗を含むすべての認証操作を記録すること。認証の種類や使用された要素などの追加メタデータも収集すべきである（V16.3.1）。認可の失敗を記録すること。L3 では、機微データへのアクセス時の記録を含め（機微データそのものは記録せずに）、すべての認可判断を記録しなければならない（V16.3.2）。
- **なぜ重要か**: パスワードスプレー、クレデンシャルスタッフィング、IDOR の探索などは、認証失敗や認可失敗のログが大量に出ることで初めて気づけます。成功ログがないと、乗っ取られたアカウントでいつログインされたか分かりません。
- **実装のポイント**: 認証・認可の判断を行う共通の場所（ミドルウェアやデコレータ）でログを出すと、記録漏れを防げます。

```python
# ✅ OK 例: 認可チェックの共通関数で失敗を必ず記録
def require_owner(resource, user):
    if resource.owner_id != user.id:
        security_log("authz_fail", user=user.id, resource=f"invoice:{resource.id}",
                     action="read", src_ip=client_ip)
        abort(404)
```

### V16.3.3 / V16.3.4 — 制御回避の試みと予期しないエラーを記録する（L2）

- **要件（意訳）**: ドキュメントで定義されたセキュリティイベントを記録し、入力検証、ビジネスロジック、アンチオートメーションなどのセキュリティ制御を回避しようとする試みも記録すること（V16.3.3）。予期しないエラーや、バックエンドの TLS 失敗などのセキュリティ制御の失敗を記録すること（V16.3.4）。
- **なぜ重要か**: 入力検証エラーや「ありえない状態遷移」は、攻撃者が探りを入れている兆候です。TLS 検証の失敗は中間者攻撃の兆候かもしれません。なお原文は、ASVS の範囲はセキュリティイベントのログ記録までで、アラートや相関分析（SIEM ルールなど）は運用・監視システムの範囲外としています。

### V16.4.1 — ログインジェクションを防ぐ（L2）

- **要件（意訳）**: すべてのログ記録コンポーネントは、ログインジェクションを防ぐためにデータを適切にエンコードすること。
- **なぜ重要か**: ユーザー入力に改行が含まれていると、攻撃者は偽のログ行を挿入できます。例えばユーザー名に `alice\n2026-11-08 INFO login success user=admin` を入れると、管理者が正常にログインしたかのような記録を作り、調査を混乱させられます。ログビューアが HTML を描画する場合は XSS にもつながります。
- **実装のポイント**: 構造化ログ（JSON）にしてライブラリにエスケープを任せるのが最も確実です。テキストログの場合は改行などの制御文字をエンコードします。

```python
# ❌ NG 例: ユーザー入力をそのまま文字列連結
logging.info("login failed for user=" + request.form["username"])

# ✅ OK 例 1: JSON で出力（改行は \n にエスケープされる）
security_log("authn_login_fail", user=request.form["username"])

# ✅ OK 例 2: テキストログなら制御文字をエンコード
def sanitize(s: str) -> str:
    return s.replace("\\", "\\\\").replace("\r", "\\r").replace("\n", "\\n")
logging.info("login failed for user=%s", sanitize(request.form["username"]))
```

### V16.4.2 / V16.4.3 — ログを保護し、別システムへ送る（L2）

- **要件（意訳）**: ログを不正アクセスから保護し、改変できないようにすること（V16.4.2）。分析・検知・アラート・エスカレーションのために、ログを論理的に分離されたシステムへ安全に送信すること。アプリケーションが侵害されてもログが侵害されないようにすることが目的である（V16.4.3）。
- **なぜ重要か**: 攻撃者はサーバを侵害すると、痕跡を消すためにまずローカルのログを削除・改ざんします。ログが同じサーバにしかなければ、何が起きたのか分からなくなります。
- **実装のポイント**: ログは TLS で集中ログ基盤（別アカウント・別権限）に転送し、アプリのサーバからは追記のみ可能・削除不可にします。

### V16.5.1 — 利用者には汎用的なエラーメッセージを返す（L2）

- **要件（意訳）**: 予期しないエラーやセキュリティ上センシティブなエラーが発生した場合、利用者には汎用的なメッセージを返し、スタックトレース、クエリ、秘密鍵、トークンなどの内部システムの機微データを露出しないこと。
- **なぜ重要か**: スタックトレースは使用しているフレームワークやバージョン、ファイルパス、SQL 文を明かし、SQL インジェクションなど次の攻撃の手がかりになります。
- **実装のポイント**: 詳細はサーバ側のログに記録し、利用者には相関用の ID だけを返します。

```python
import uuid

# ❌ NG 例: 例外内容をそのまま返す
@app.errorhandler(Exception)
def handle(e):
    return {"error": str(e), "trace": traceback.format_exc()}, 500

# ✅ OK 例: 詳細はログへ、利用者には汎用メッセージ + 問い合わせ用 ID
@app.errorhandler(Exception)
def handle(e):
    error_id = uuid.uuid4().hex
    logging.getLogger("app").exception("unhandled error id=%s", error_id)
    return {"error": "Internal server error", "error_id": error_id}, 500
```

### V16.5.3 — フェイルオープンにしない（L2）

- **要件（意訳）**: 例外が発生した場合も含め、アプリケーションが穏やかかつ安全に失敗し、検証ロジックでエラーが起きたにもかかわらずトランザクションを処理してしまうようなフェイルオープン状態を防ぐこと。
- **なぜ重要か**: 「チェック処理で例外が出たら、とりあえず通す」という実装は、攻撃者が意図的に例外を起こさせることで検証を回避できてしまいます。

```python
# ❌ NG 例: 不正検知サービスがエラーなら素通り（フェイルオープン）
def is_allowed(tx):
    try:
        return fraud_api.check(tx)
    except Exception:
        return True

# ✅ OK 例: エラー時は拒否（フェイルセキュア）し、記録する
def is_allowed(tx):
    try:
        return fraud_api.check(tx)
    except Exception:
        security_log("security_control_failure", control="fraud_check", tx=tx.id)
        return False
```

### V16.5.4 — 最終手段のエラーハンドラを定義する（L3）

- **要件（意訳）**: 処理されなかったすべての例外を捕捉する「最終手段（last resort）」のエラーハンドラを定義すること。ログに残すべきエラーの詳細を失わないためと、エラーによってアプリケーションのプロセス全体が停止して可用性が失われるのを防ぐためである。
- **補足**: 原文の注記によると、Swift や Go、そして一般的な設計慣行として多くの関数型言語は、例外や最終手段のイベントハンドラをサポートしません。その場合は、その言語やフレームワークに適した方法で、例外的・予期しない・セキュリティ関連のイベントを安全に扱えるようにします。

## 4. よくある脆弱性・アンチパターン

- **ログに認証情報やトークン**: リクエストボディやヘッダ（`Authorization`、`Cookie`）を丸ごとデバッグ出力し、そのまま本番に残っている（V16.2.5）。
- **成功ログがない／失敗ログがない**: 認証失敗だけ、または例外だけを記録し、認証成功や認可失敗が残らない（V16.3.1, V16.3.2）。
- **ローカルタイムでばらばらのタイムスタンプ**: サーバごとにタイムゾーンが違い、時刻同期もされていない（V16.2.2）。
- **非構造化で解析できないログ**: 自由形式のテキストで、ログ基盤がパースできない（V16.2.4）。
- **ログインジェクション**: ユーザー入力を文字列連結でログに出す（V16.4.1）。
- **ログがアプリサーバ上にしかない**: 侵害時に攻撃者が削除できる（V16.4.2, V16.4.3）。
- **棚卸しされていない記録先**: 開発者が個人的に追加した外部ログサービスや、デバッグ用のファイルに機微データが出力されている（V16.1.1, V16.2.3）。
- **スタックトレースの表示**: 本番で詳細なエラーページや例外メッセージを返す（V16.5.1。関連して V13.4.2 デバッグモード）。
- **フェイルオープン**: 例外時に認可チェックや検証を素通りさせる（V16.5.3）。
- **依存先の障害で全体停止**: 外部 API がタイムアウトするとアプリ全体が応答しなくなる（V16.5.2）。サーキットブレーカーやグレースフルデグラデーションを使う。

## 5. 検証（テスト）のヒント

- **ログ棚卸しの確認**: 各層（Web サーバ、アプリ、DB、クラウド基盤など）について、記録イベント・形式・保存先・用途・アクセス制御・保持期間を記載したインベントリがあるか確認し（V16.1.1）、実際の出力先がそれと一致するかを確認します（V16.2.3）。
- **イベントの発生テスト**: ログイン成功・失敗、権限のないリソースへのアクセス、不正な入力などを実際に行い、期待するログが必要なメタデータ付きで出力されるかを確認します（V16.2.1, V16.3.x）。
- **機微データの grep**: テストで使ったパスワードやトークンの文字列でログを検索し、平文で残っていないことを確認します（V16.2.5）。
- **ログインジェクション**: ユーザー名などに `\r\n` や偽のログ行を含めて送信し、ログ上で 1 行として扱われ、エスケープされていることを確認します（V16.4.1）。
- **ログの保護**: アプリの実行ユーザーでログを削除・改変できないか、集中ログ基盤へのアクセス権限が適切か確認します（V16.4.2, V16.4.3）。
- **エラーメッセージ**: 不正な型、極端に長い値、存在しない ID、壊れた JSON などを送り、スタックトレースや SQL・内部パスが返らないことを確認します（V16.5.1）。
- **障害注入**: 依存する DB や外部 API を停止・遅延させ、アプリが安全に縮退するか、検証がフェイルオープンにならないかを確認します（V16.5.2, V16.5.3）。

## 6. 確認問題

**Q1.** V16 の要件数と L1/L2/L3 の内訳を答えてください。

<details><summary>答えと解説</summary>

全 17 要件で、L1: 0 / L2: 16 / L3: 1 です。唯一の L3 要件は V16.5.4（最終手段のエラーハンドラ）です。

</details>

**Q2.** セッショントークンをログに記録する必要がある場合、V16.2.5 に照らしてどのように扱うべきですか。

<details><summary>答えと解説</summary>

データの保護レベルに基づいてログ記録を制御し、セッショントークンのようなデータは全体または一部をハッシュ化・マスクした形でのみ記録します。認証情報や決済情報などは記録自体が許されない場合があります（V16.2.5, L2）。

</details>

**Q3.** 認可に関するログについて、L2 と L3 で求められる範囲の違いを説明してください。

<details><summary>答えと解説</summary>

L2 では認可の失敗を記録すれば足ります。L3 では、機微データへのアクセスの記録を含め（機微データそのものは記録しない）、すべての認可判断を記録しなければなりません（V16.3.2）。

</details>

**Q4.** 次のコードの問題点を、該当する要件 ID とともに指摘してください。

```python
try:
    ok = validate_payment(req)
except Exception:
    ok = True
if ok:
    process_payment(req)
```

<details><summary>答えと解説</summary>

検証ロジックで例外が発生した場合に処理を通してしまうフェイルオープン状態です。V16.5.3（L2）は、検証エラーにもかかわらずトランザクションを処理するようなフェイルオープン状態を防ぎ、安全に失敗することを求めています。例外時は `ok = False` として拒否し、V16.3.4 に従ってセキュリティ制御の失敗として記録すべきです。

</details>

**Q5.** ログをアプリケーションと同じサーバのローカルファイルにのみ保存している場合、どの要件を満たしていませんか。また、その理由は何ですか。

<details><summary>答えと解説</summary>

V16.4.3（L2）を満たしていません。ログは分析・検知・アラート・エスカレーションのために論理的に分離されたシステムへ安全に送信する必要があります。アプリケーションが侵害されても、ログが一緒に侵害（削除・改ざん）されないようにするためです。

</details>
