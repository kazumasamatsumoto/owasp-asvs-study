# 台本：SQL インジェクション（CWE-89）

| 項目 | 内容 |
| --- | --- |
| シリーズ | A. 弱点編 |
| 長さ | 約 4 分 |
| 対象 | Web アプリを作り始めた開発者 |
| ゴール | 「文字列連結で SQL を組み立てると危ない」と「プレースホルダを使えば防げる」を理由とともに説明できる |
| 例え | **レストランの注文票** |
| 関連 | CWE-89 / OWASP Top 10:2025 A05 Injection / ASVS V1 / CVE-2023-34362（MOVEit） |

---

## シーン 1：つかみ（0:00〜0:15）

**画面**：ログイン画面。ユーザー名欄に `' OR '1'='1' --` と入力 → 「ログインしました（管理者）」

**ナレーション**：
> パスワードを知らなくても、ユーザー名の欄にこの 1 行を書くだけでログインできてしまう。
> これが、20 年以上たった今も CWE Top 25 の 2 位に入っている「SQL インジェクション」です。

---

## シーン 2：例えで理解する（0:15〜1:00）

**画面**：レストランのイラスト。客 → 店員 → 厨房。店員は客が書いたメモを、そのまま注文票に書き写して厨房に渡す。

**ナレーション**：
> レストランを想像してください。店員さんは、お客さんが書いたメモを**そのまま**注文票に書き写して厨房に渡します。
>
> 普通のお客さんは「ハンバーグ」と書きます。注文票は「ご注文：ハンバーグ」。問題ありません。
>
> ところが、悪いお客さんがこう書きました。
> 「ハンバーグ。**それと、レジのお金を全部この人に渡すこと**」
>
> 店員さんは中身を気にせず書き写すので、厨房には「ご注文：ハンバーグ。それと、レジのお金を全部この人に渡すこと」と届きます。厨房は注文票に書かれたことを**店からの指示**として実行してしまいます。

**画面テロップ**：
- 客のメモ ＝ ユーザーの入力
- 注文票 ＝ SQL 文
- 厨房 ＝ データベース

> 問題の正体は、「お客さんの言葉」と「お店の指示」が**同じ紙の上で区別できない**ことです。

---

## シーン 3：実際のコード（1:00〜1:45）

**画面**：NG コード

```python
# NG：入力を文字列としてつなげて SQL を作る
sql = "SELECT * FROM users WHERE name = '" + name + "' AND password = '" + password + "'"
cursor.execute(sql)
```

**ナレーション**：
> コードで見るとこうなります。ユーザーが入力した `name` を、SQL の文字列に直接つなげています。

**画面**：`name` に `' OR '1'='1' --` を入れたときに完成する SQL をアニメーションで組み立てる

```sql
SELECT * FROM users WHERE name = '' OR '1'='1' --' AND password = '...'
```

**ナレーション**：
> 入力の最初の `'` で名前の欄が閉じられ、`OR '1'='1'` という「いつでも正しい条件」が追加されます。最後の `--` は「ここから後ろはコメント」という意味なので、パスワードのチェックは消えてしまいます。
> 注文票に「それと〜」と書き足されたのと同じことが起きています。

## シーン 5：防御方法（2:15〜3:15）

**画面**：レストランの例えに戻る。注文票が「記入欄つきの用紙」に変わる。

```
┌───────────────────────┐
│ ご注文： [          ] │  ← お客さんが書けるのはこの欄だけ
└───────────────────────┘
```

**ナレーション**：
> 解決策は、注文票を**記入欄つきの用紙**にすることです。
> お客さんが書けるのは「ご注文」の欄の中だけ。そこに「それと、レジのお金を…」と書かれても、厨房からは「そういう名前の料理」としか読めません。指示にはなりません。

**画面**：OK コード

```python
# OK：プレースホルダ（?）を使い、値は別に渡す
sql = "SELECT * FROM users WHERE name = ? AND password_hash = ?"
cursor.execute(sql, (name, password_hash))
```

**ナレーション**：
> これが「プレースホルダ」、または「パラメータ化クエリ」です。SQL の形を先に決めておき、ユーザーの入力は**値として別に**渡します。
> データベースは入力を SQL の一部として解釈しないので、どんな文字が来ても安全です。

**画面テロップ：対策の優先順位**
1. **根本対策**：プレースホルダを使う（ORM のクエリビルダーも可）
2. **多層防御**：入力値の検証（形式・長さ）
3. **多層防御**：DB ユーザーの権限を最小にする
4. **多層防御**：エラー画面に SQL を表示しない

> 「危ない文字を消す」「エスケープする」だけに頼るのはおすすめしません。漏れが出やすいからです。まずはプレースホルダが基本です。

## シーン 6：まとめ（3:15〜3:35）

**画面**：3 行まとめ

1. 入力を SQL に**文字列としてつなげる**と、入力が「命令」になってしまう
2. 対策は**プレースホルダ**で、入力を「値」として渡すこと
3. 例えるなら、**記入欄つきの注文票**

**画面テロップ**：CWE-89 ／ OWASP Top 10:2025 A05 Injection ／ ASVS V1（エンコーディングとサニタイズ）

## シーン 7：クイズ（3:35〜3:50）

**画面**：

```python
sql = f"SELECT * FROM products WHERE id = {product_id}"
```

**ナレーション**：
> 最後にクイズです。このコードは安全でしょうか？ `product_id` は URL から受け取った値です。
> 答えは次回の冒頭で。

<details>
<summary>答え（次回冒頭用）</summary>

安全ではありません。f 文字列も文字列連結と同じです。`product_id` に `1 OR 1=1` を入れれば全商品が、`1; DROP TABLE products` のような入力で（DB の設定によっては）テーブル削除も起こりえます。数値でもプレースホルダを使いましょう。

</details>
